# UI behavior rules (v3 style): Other

Part of the `v3-ui-style` skill. Companion to `references/v3-design-principles.agents.md` (look, behavior principles, interaction rules, what not to copy). The skill's SKILL.md maps ID prefixes to area files. Paths are relative to the skill folder.

How to read:

- One bullet is one behavior with a stable ID (`DS-1`). A rule may name rules of other areas by ID; when your screen uses that part, read those rules too.
- **Pitfall** marks a behavior whose history shows a failed earlier attempt, a revert or a fixed bug. It says what went wrong and what fixed it. Do not skip it: it is the reason the behavior is shaped the way it is.
- `v3:` gives the v3 helper and `file:line` in the bundled code under `references/v3-code/`, a copy of the mailcow Logs Viewer frontend at commit `0210d15` (`ui.css` is under `assets/css/`). Start at the cited lines and widen to the whole function and what it calls when the bullet is not enough. The rules were first written against the earlier snapshot `deb075d`, then checked rule by rule against this code.
- Rules the interaction fixes changed (October 2026) start with what v3 does now and name its helpers; the part marked "Before the interaction fixes" describes the code before them. Where the two differ, the first part is the rule; details the first part does not cover still hold.
- The principles file's section "Interaction rules v3 follows since its interaction fixes" lists what those fixes added. Never copy anything listed there under "Do not copy".

## Other

- **OT-1 "hidden" always wins; empty wrappers disappear.** Anything JS hides stays hidden whatever the stylesheet order, with no flash before CSS loads: `.hidden[class*="ui-"] { display: none !important }` plus an inline `<style>.hidden{display:none}</style>` in `<head>` before any stylesheet; many components also carry an explicit `.X.hidden { display: none }`. No component combines `hidden` with a responsive display utility. A wrapper whose children are all hidden takes no space, so rows that would hold only hidden items disappear: `:not(:has(> :not(.hidden)))` on `.ui-head-slot`, `.ui-head-links`, `.ui-dmarc-sync`, `.ui-head-tools`; `:empty` on `.ui-h1-note`, `.ui-md-header`, `.ui-flow`, `.ui-topbar-actions`, `.ui-msg-more`. Pitfall: without the always-wins rule "Loading settings..." stayed visible after loading, because component classes beat the compiled utility `.hidden` (#267). v3: ui.css:145-149, 559, 574, 1256, 2295, 2389, 2843, 2849, 2863-2866; index.html:19-20.
- **OT-2 Pages opt in by markup; shared behavior wires itself.** Sorting, dialog-to-sheet, pickers, filter changes and Back history work on every page without page code: a page opts in only by markup and class names, and one shared component exists per behavior, built by reference (one count helper replaced per-page variants). Wire it globally with document-level delegated listeners and `MutationObserver`s batched with `requestAnimationFrame`. Markup contracts: TB-1, DS-1, MP-3, DS-10. v3: `uiLocked`, `uiSaveBar`, `uiSheetShow`, `uiPicker`; utils.js:1151, 1303-1310, 1626-1640, 1816-1911; router.js:531-540.
- **OT-3 A documented z-index ladder.** Layers never fight; document one ladder and use only its values: toast `100000` > confirm `99999` > phone search sheet `90` > bottom sheet `70` > save bar `60`, flyout `60` > dialog backdrop `50`, popover `50`, container-log dialog `50` > phone search while a message is open `49` > global search panel `45` > menus and Mailbox Stats dropdown `40` > tab bar `36` > More menu `35` > phone top bar `30` > settings mobile nav `20` > page tabs on phones `6` > Messages search bar `5` > Security filter head `4` > chart tooltip `3` > timeline head `2` > reading gauge `-1` (inside an isolated stacking context, see DS-15). Popover menus use the browser top layer. v3: ui.css:383, 446, 648, 846, 894, 1148, 1166, 1174, 1643, 1759, 1924, 1968, 2090, 2102, 2164, 2232, 2459, 2504, 2519, 2612, 2615, 2783; index.html:1542.
- **OT-4 Theme follows the system until chosen, applied before paint.** The theme follows `prefers-color-scheme: dark` until the user chooses, then the choice is kept in `localStorage.theme` = `dark` | `light` and applied as class `dark` on html before anything draws, also on the login page. The toggle icon shows the other theme. Native controls (checkboxes, date pickers, selects, scrollbars) and help tables follow the theme: `:root { color-scheme: light }`, `.dark { color-scheme: dark }`, markdown `color-scheme: inherit`. Scrollbars are thin and themed: `scrollbar-width: thin`, color `rgb(156 163 175 / .6)` (dark `rgb(75 85 99 / .8)`), webkit `8px`, thumb radius `9999` with a `2px` transparent border; `#recent-activity::-webkit-scrollbar { display: none }`. Pitfall: the full light, dark and phone tour (#279) found the phone top bar title unreadable in dark mode and established that native controls follow the theme through `color-scheme`; in #285 help followed the OS theme and showed dark tables in light mode (DS-19). v3: `initDarkMode`, `toggleDarkMode`; app.js:5138-5165; login.html:129-142; ui.css:1070-1072, 2179-2189, 2511; index.html:85-130.
- **OT-5 Tabular numbers.** Counts and times do not jitter when they update: `font-variant-numeric: tabular-nums` on every live number (counts, KPIs, times, badges, search counts). v3: ui.css:140, 207, 214, 293, 308, 1103, 2467.
- **OT-6 Session memory for view choices; few stored preferences.** Within the session the app remembers view choices across page switches in memory: Messages and Security filters, the quarantine sort, the Status container and job filters, opened job groups and blocklist panels, expanded mailboxes, opened aliases, the domain tab per domain, the DMARC daily fold, the open blocked sender, the quick filter fold, the active Statistics/Rate Limits view, rate-limit filters and bulk input. Persist only what a user would expect to survive a reload, per browser: `localStorage.theme`, `navCollapsed`, `logsNewestFirst`, `authOffBannerDismissed`. v3: `currentFilters`, `quarantineSortOrder`, `statusCtrFilter`, `statusJobFilterValue`, `statusJobsOpen`, `mailboxStatsCache`, `domainTabs`, `dmarcState.daysOpen`; app.js:195-199, 2809, 4073-4074, 4633-4637, 4910; logs-viewer.js:17, 219, 547; mailbox-stats.js:17-18, 28; domains.js:13; dmarc.js:507; rate-limits.js:32-49.
- **OT-7 Nothing is lost in a rebuild.** A redesign never silently drops behavior: every id, handler, gated state, option and visible word of the old markup is still there, checked against an inventory of ids, handlers and words, catalog checks, a self-checking conversion and a link comparison with the previous build. Older templates are mapped onto the new tokens so they look like the new design in both themes: legacy selectors under `.ui-main` start with `html body` to outrank utilities, legacy primary hover `accent 85%` mixed with bg, placeholder muted `.8`. v3: ui.css:1020-1065.
- **OT-8 Details tell the story first, technical values last.** A message's details read as a story: under the subject, From, To (N) and When, one sentence says the outcome in its tone ("Delivered to the folder "Junk"", "Deferred, Postfix will try again", "Bounced back to the sender"). "What happened" lists the delivery as steps with a small time label above each ("Received from 1.2.3.4", "Queued as ABC123", "Delivered to mx.example.com"), IDs copyable in the steps; steps in the same second keep mail-flow order (receive `0`, queue `1`, Rspamd `2`, deliver `3`, Dovecot `4`), a retried step collapses into one line with "N attempts", empty state "No delivery steps recorded yet."; relay host parsed from `host[ip]:port`. A mailbox verdict banner shows only when it needs explaining (discarded, rejected, failed, forwarded), Dovecot icons with tones muted, fail, warn, info. A message delivered several times shows a collapsed "Delivery journey" listing every leg, the current one tagged "viewing" (chevron `180deg` `.15s`). Identifiers come last as a quiet list of technical values: client IP with flag, place and network owner, authenticated user, then queue ID and message ID. A missing subject is filled from a sibling delivery of the same Message-ID; the placeholder "Postfix Log Details" counts as no subject. The content always shows something readable: `plainText && plainText !== '-' ? text_plain : text_html` in `<pre dir="auto">`. Keyboard: the Delivery journey header is `role="button"` with `tabindex="0"`, `aria-expanded` and `aria-controls="delivery-journey-legs"`, every leg but the current one is `role="button"` with `tabindex="0"`, and both open on Enter and Space (`data-row-open`, AX-5). Screen reader: steps are an `<ol>` with `<time datetime>`, Identifiers a `<dl>`, the current leg carries `aria-current="true"`. Pitfall: #285 went through five commits: trimming the timeline and then Identifiers "made the details harder to read", so both were restored, then Identifiers became a label and value list with IDs copied from the timeline, then technical values only. #316 moved each step's time above it "like a timeline"; #340 put who sent it first and the IDs, which are only copied, last. v3: app.js:3166-3169, 3193-3197; message-details.js:171-247, 316-466, 477-580; ui.css:460-470.
- **OT-9 A summary in the header opens its full tab.** The spam score, action and class (SPAM/CLEAN) sit in the outcome bar at the top of a message with a chevron; clicking it opens Spam Analysis. Score red when `>= required_score` (fallback `15`), else green, `2` decimals. The Security tab label gets a red count of the security events, as on the page tabs (`<span class="ui-tab-n is-fail" title="Security events">N</span>` after `<span>Security</span>`), and no count when there are none; closing the message resets the label to `<span>Security</span>`. The tab lists the events ("Security Events Detected: 3 authentication event(s) from the sender's IP within 1 hour of this message") or says "No security events detected". Keyboard: the summary is a `<button title="Open Spam Analysis">`, chevron `aria-hidden`; the tab is a `role="tab"` button with `aria-selected`, and the count is text inside it. v3: message-details.js:451-459, 823, 862-886; ui.css:583-587, 1366-1367.
- **OT-10 The Security list model.** The Security page is one list for a period picked above it (default `1D`; the same period drives the list, the count and the panels): every address that tried, split into To review (not banned, tagged with the rule that caught it, or Allowlisted) and Banned (by Fail2ban, a rule or the denylist), built on the server from every source with real counts and paged. A Fail2ban network ban is a row of its own, named by its network, that does not open ("Banned" "by Fail2ban" with a "Whole network, N addresses" tag, IPv6 only "Whole network"; "Every address from A to B is blocked."), and each address banned with it is tagged "Banned" "through <network>", where Unban lifts the whole network. Each country bar (`n / max * 100%`, watched dot `7px`) is split into to review (amber) and banned (red) parts with a legend; clicking a country bar or a network filters the list and clicking again clears it, shown as a dark chip with X. Row details give origin, failed logins (counted for the chosen period as the list counts them: "12 in the last 24 hours", "12 in the last 7 days", "12 since Oct 3" when the logs start later; an address with none there has the last 24 hours counted from its own `40` log lines: "40+" when the sample is saturated, "None in the last 24 hours. The last was 3 days ago"), which rules caught it, accounts tried, what the rules said, the raw log and "All events of this address". History, loaded on first open, keeps closed catches as static rows with honest tags ("No new activity" for a watch-mode catch, "Ban ended" for an enforced one, "Ban undone", "Dismissed"). The allowlist and denylist explain each entry ("Failed 12 logins in the last 24 hours, never banned", "Added by hand, still tried 3 times in the last 24 hours"); an entry a rule wrote is removed through the rule (Undo); a single IPv6 address an earlier version wrote as a `/32` network is tagged "Whole network" with Repair (after a confirm, replaced by the `/128` address) and Remove. Keyboard: address rows are `role="button"` with `tabindex="0"` and `aria-expanded`, and open on Enter and Space when the row itself has the focus; bars and networks are buttons with `aria-pressed`; the X has `aria-label="Show every country"` / `"Show every network"`. Pitfall: #348 had four lists (To review, Banned, Tried not banned, History); #365 reduced them to two because "An address is banned or it is not" and moved quiet watched catches to history after 7 days; #366 replaced a list built from "the 50 busiest addresses of the last day, up to 500 rule catches" with a server-built list with the real count; #386 made one period rule the list, the count and the panels, and kept allowlisted addresses visible instead of letting them disappear. v3: security.js:107-117, 316-335, 392-402, 436-504, 524, 549-604, 698-701, 719-851; protection.js:127-139; ui.css:708-709, 738-739.
- **OT-11 Dashboard Security card and health cards.** The dashboard Security card shows the Security page's two lists with the same real counts as buttons ("To review", "Banned now" red above zero), each opening its list; hovering or focusing a number underlines it. Below, "Protection N of M on" with a mark lists the active protections joined by `" · "` (Outgoing spam counts as off, "needs a Read-Write key", while that key is missing); clicking unfolds every protection as a button that opens its settings card (chevron `rotate(45deg)` -> `rotate(-135deg)`). On a wide screen the card tops the side column; in one column it comes right after Needs attention. Health cards show a big value, a tone and a note ("11 of 12 healthy", "Up to date", or "Update check failed" when the latest version could not be read, "N of M running", storage "% used", amber above `75%`, red above `90%`); the blocklist card covers "No check yet; the first one runs by itself", "1 of 2 listed", "Check error", "2 clean". Mailcow system figures show totals with "N active". Dashboard figures are entry points into their lists (NL-12). Keyboard: the fold-out has `aria-expanded`, `aria-controls="dashboard-protections"`. v3: app.js:2203-2329, 4301-4348, 4572-4600; ui.css:1219-1234.
- **OT-12 Recognised names are a recognition, not a fact.** Devices names the mail app and a Samsung model code when it recognises them; an unrecognised app gets no name; the app name shows only when it differs from the device name, with a tooltip explaining it is a recognition, not a fact. The device ID sits in the name's tooltip and in the search. New devices get a "New" tag, long-unseen ones a muted Last seen (thresholds `new_days`, `stale_days` from the API); failing requests get a red tag ("Sign-in failed", "Refused", "Error N") only for HTTP `400` and above, tooltip "SOGo answered HTTP N". Without GeoIP the page says what the location needs instead of dropping the column. Screen reader: device name in `<bdi>`, flag `alt=""`. Pitfall: #370 dropped the Devices summary cards and kept the IP on one line on phones, then added naming of the mail app and Samsung model, then called the Android app Gmail and moved the device ID into a tooltip. v3: devices.js:119-139.
- **OT-13 A demo notice that says what visitors see.** Every demo page opens with a slim, operator-configurable notice (fictional data, no real mail server, changes reset on a schedule, a link to the installation guide) that follows the theme and shortens on narrow screens; the operator can replace the whole text. Pitfall: #303 first named the reset time ("every night at 00:00 in the demo's time zone"), then said the demo resets on a schedule instead of naming the time, then let the notice carry a preview label, then let the operator set the whole notice text.
- **OT-14 Branding everywhere.** One app-info source is read by every surface: the configured app title appears in the sidebar, browser tab (after the page and its open tab: "Mailbox Stats · Rate Limits · mailcow Logs Viewer"), phone top bar and footer; a configured logo replaces the default in the sidebar and phone top bar (and on the login page, FS-23). v3: `loadAppInfo`, `queueDocumentTitle`; app.js:550-563, 571-593.
- **OT-15 A record window that lets you try a policy and copy the record.** The DMARC domain view has a Records card (DMARC, SPF, DKIM, TLS-RPT), each row with a one-line state, a status tag and a chevron, opening its own record window. Policies are named by what they protect: none "Monitoring" (red), quarantine "Partial" (amber), reject "Enforced" (green), no record a solid red "Missing". SPF reads "97% of mail aligned", OK at `95%` and up, else Gaps; DKIM "Your mail is signed" or "No signed mail in the reports". The DMARC window explains what is published (alignment read as relaxed or strict) and its notes, lets the user try the next stricter policy (AX-7), says for quarantine or reject how many messages that failed DMARC in the last 30 days receivers would have refused or sent to spam ("Ready." only with mail and when every sender that passes on most of its mail passes on `95%` or more; "No data." without mail), and offers a ready record with Copy: `_dmarc.<d> TXT "<record>"`, the published record with only `p=<pick>` changed so its other tags stay, or `v=DMARC1; p=<pick>; rua=mailto:dmarc@<d>` when there is none; the TLS-RPT window offers `_smtp._tls.<d> TXT "v=TLSRPTv1; rua=mailto:<imap user or tls-reports@d>"` pointing at the mailbox this page reads. Only `mailto:` report addresses become links (case-insensitive `^mailto:`). A sender page carries one verdict tag ("Fails DMARC" below `50%` pass, "Passes on DKIM only" when SPF is below `50%`, "Passes"); a failing sender adds what to do if it is yours and what the policy does if it is not. Keyboard: record rows are `<button>`s, chevron `aria-hidden`; the policies are a radio group. Pitfall: before #434 SPF and DKIM "opened the DMARC record window"; now each opens its own, and the policies became a radio group (the window itself came in #385). Until #441 the ready record was rebuilt from `p` and the first report address, dropping the record's other tags, and a second top-level `dmarcPolicyTag` declaration replaced the home list's helper, so every domain read Missing; the home list's helper is now `dmarcDomainPolicyTag`: keep one top-level declaration per name. v3: `DMARC_POLICY_LEVEL`; dmarc.js:478-490, 587-719, 767-772.
- **OT-16 Checks with the evidence folded.** Each domain gets SPF, DKIM, DMARC, DNSSEC, DANE and MTA-STS checks (OK, Warning, Error or "-"), tooltip per cell `"<check>: <message>"`, with one summary sentence for the page ("7 domains, 1 inactive. 2 need a DNS change." or "DNS looks right.") and "Updated 3h ago"; only SPF, DKIM and DMARC count as issues. Each check is a card with its message (cards `3` per row, one column on phones); the evidence is folded in native `<details>`: "View Record", "Checked IPs (N)" with each IP's source and Authorized / Not authorized, warnings and info, and "Expected Value" only when the check failed. Records copy on click. Alias domains list with a dot per check and open their own cards, with the note "These domains deliver to the same mailboxes and send with their own DNS records". Keyboard: native disclosure; the domain row's chevron is a `<button class="ui-row-chev">` with `aria-expanded` and `aria-controls`; the alias header is a `<button>`, dots carry a `title` and are `role="img"` with the same text as `aria-label`. v3: domains.js:11-87, 173, 264-336; ui.css:1512-1515.
- **OT-17 External lookup links are safe.** Validate the scheme before rendering any external link: provider lookup links render only for `https://` URLs and open in a new tab with `rel="noopener noreferrer"`, so the opened page gets no access to the app. v3: app.js:4120-4124, 4641-4643.
