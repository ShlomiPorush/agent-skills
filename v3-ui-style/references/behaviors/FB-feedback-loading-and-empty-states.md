# UI behavior rules (v3 style): Feedback, loading and empty states

Part of the `v3-ui-style` skill. Companion to `references/v3-design-principles.agents.md` (look, behavior principles, interaction rules, what not to copy). The skill's SKILL.md maps ID prefixes to area files. Paths are relative to the skill folder.

How to read:

- One bullet is one behavior with a stable ID (`DS-1`). A rule may name rules of other areas by ID; when your screen uses that part, read those rules too.
- **Pitfall** marks a behavior whose history shows a failed earlier attempt, a revert or a fixed bug. It says what went wrong and what fixed it. Do not skip it: it is the reason the behavior is shaped the way it is.
- `v3:` gives the v3 helper and `file:line` in the bundled code under `references/v3-code/`, a copy of the mailcow Logs Viewer frontend at commit `ab0f644` (`ui.css` is under `assets/css/`). Start at the cited lines and widen to the whole function and what it calls when the bullet is not enough. The rules were first written against the earlier snapshot `deb075d`, then checked rule by rule against this code.
- Rules the interaction fixes changed (October 2026) start with what v3 does now and name its helpers; the part marked "Before the interaction fixes" describes the code before them. Where the two differ, the first part is the rule; details the first part does not cover still hold.
- The principles file's section "Interaction rules v3 follows since its interaction fixes" lists what those fixes added. Never copy anything listed there under "Do not copy".

## Feedback, loading and empty states

- **FB-1 Locked, not hidden.** When a feature needs something missing (a Read-Write API key, a password, a licence, IMAP, a setting), the control never just disappears. Either keep it visible but `disabled` with the reason in `title` ("Fetching reports needs IMAP set up in Settings"), or put a dashed locked box in its place: lock icon, bold title ("Ban, Allow and Unban are locked"), the reason naming the missing key or variable, and an Open Settings button (on phones under the text); box grid `20px minmax(0, 1fr) auto`, `border: 1px dashed muted 55%`, full-page variant `min-height: 50vh`. Shared reason text: "needs a Read-Write API key (MAILCOW_API_KEY_RW). Configure it in Settings -> Mailcow -> Connection.". Repeat the note inside a dialog when the list note is hidden behind it; tabs and sub-menus stay present; rules say what they can see ("Only SMTP logins are checked. IMAP logins need Live Logs to be on."). When the key status arrives after the page drew, draw actions and locks again. Locked abuse controls keep the activity readable, hide buttons and disable the textarea, and distinguish a missing key (Open Settings) from protection being off (points to the card's switch); read-only maps get `readonly aria-readonly="true"`; a disabled Reset button still stops the row click. The About page shows one card per dependency saying whether it is set up and working, with a Settings button; the Read-Write key and Rspamd cards give the last credential check of the saved key ("Accepted", or what was wrong; "It has not been checked yet." before the first). Keyboard: native `disabled` plus `title`; lock icon `aria-hidden`. Pitfall: parts of the app disappeared when a key or setting was missing with nothing saying why (#337), and #262 replaced a yellow banner, an overlay and silently missing buttons with this component (#256). A switched-off job used to show "idle" and silently lose its Run button (#264), and the map editor now opens read-only instead of offering a Save that fails (#293). The one reversal: #433 hides Upload Report again when manual upload is off, following Settings without a reload. v3: `uiLocked(title, trustedHtml, action = 'settings' | customHtml | '')`, `.ui-locked`, `.ui-disabled-page`, `UI_RW_KEY_TEXT`; utils.js:179-192; ui.css:247-264, 1023-1026, 1272-1276, 2194-2196; app.js:447-458, 1476-1477, 3128, 3399, 3716-3741; security.js:634-635, 836, 1155-1210, 1254-1293; about.js:75-81.
- **FB-2 Toasts: one at a time, four seconds by default, announced, with one action.** Every action ends in a toast at the bottom end corner (`position: fixed; bottom: 18px; inset-inline-end: 18px; z-index: 100000; max-width: min(420px, calc(100vw - 36px))`) with a 4px colored start border and an icon by type (`'success' | 'error' | 'warning' | 'info'`; unknown types fall back to info). A new toast replaces the current one instead of stacking. It stays `4000ms` by default or its own `duration` (`Infinity` keeps it until closed, used for Retry and Refresh), then fades (`opacity .3s`) and is removed after `300ms`; it waits while the pointer or the focus is on it, then gives the rest of its time (at least 1.5 seconds), and a fading toast caught by the pointer, the keyboard or a click on its action comes back for 1.5 seconds. It can be closed earlier with X. A toast can carry one action button (`ui-toast-action`: Undo, Retry, Refresh) with an optional `ariaLabel` that names what it acts on; a click runs `onAction` and closes the toast, and an action that returns a promise holds the toast until it settles (further clicks ignored), so the message that follows takes over. Long text wraps anywhere. On phones it sits above the tab bar at `bottom: 76px`. Keyboard: when the keyboard was in the toast being replaced, it moves to the new one (its action button, else its X); a running action keeps the keyboard in its toast and marks its button `aria-disabled="true"`. Screen reader: errors `role="alert"`, others `role="status"`; icon `aria-hidden`; close `aria-label="Close"`. v3: `showToast(message, type, { action: { label, ariaLabel, onAction }, duration })`; utils.js:650-753; ui.css:2258-2271, 2286.
- **FB-3 Errors say what failed and what to do.** Failures say what failed and what to do next: "Could not load this: <reason>. Try again in a moment.", "Failed to load <thing>: <reason>", where the reason is the server's own message (else "HTTP <status>"), never "Internal server error"; a validation error (FastAPI 422) reads each field as "field: problem" (`uiApiErrorText`). When mailcow does not answer, pages say "mailcow did not answer. Try again in a moment."; when Fail2ban does not answer, Security says so instead of showing nothing banned (ban buttons hidden, "No answer" on the card). Lists that can be retried show a Retry button; the count next to a failed list is cleared; settings show "Failed to load settings" in place of the spinner. CSV export checks first (HEAD with the current filters, then a temporary `<a download>`) and explains: "Download started.", "No data to export. Try different filters." (404), "Could not export CSV. Check the filters and try again." (422), "Could not export CSV. Refresh the page and try again." (not CSV), "Could not export CSV. Please try again.". Screen reader: error toasts are alerts. Pitfall: a failure reached the route as an unknown exception and the page showed "Internal server error" (#392, #395, issue #384); carry the server reason through. An unreachable service looked like nothing banned until #348 made the Overview say mailcow did not answer. v3: `responseError`, `uiApiErrorText`; export.js:5-41; app.js:112-121, 2956-2958, 3071-3073, 3369, 4530-4531, 4791, 4840; security.js:636-642, 785-787, 1268; settings.js:1474-1482; utils.js:898-913.

- **FB-7 Busy buttons say what is happening, then the result.** Long actions set `disabled` on their button and change its words ("Fetching...", "Unbanning...", "Allowing...", "Banning...", "Running..." with a spinning icon, "Checking...", "Signing in..." with the small `.ui-spin` ring), then restore the label in `finally`, or show a check and "Done" (reverts after `3000ms`) or "Error" (after `2000ms`) before returning by themselves. - **FB-8 No data is not a failure.** Distinguish "zero of something" from "nothing to measure" in every rate: a rate with nothing behind it (no messages, no TLS sessions) shows a muted "-" instead of a red 0%. Without mail in the period, SPF and DKIM say "No mail in the last 30 days" with a "No data" tag. The DMARC home "Passed DMARC" figure is the volume-weighted average, 1 decimal, in its tone, or a muted "-" with no messages. A domain with reports that is not on this server gets a small superscript "Not on server" (tooltip "This domain is not on this server."; on phones it reads beside the domain); nothing is marked while the server's domains are unknown. Status says "Everything is running. Nothing needs you right now." only once containers and jobs have both loaded; until then a spinner. A Dashboard card whose source did not answer says "Unknown", never a made-up value: Mail storage with "mailcow did not answer", Message linking with "Could not count", To review and Banned now with "Fail2ban did not answer" (an error answer with HTTP 200 counts as no answer), and "-" until the first answer; a trend breaks where an hour has no sample instead of dropping to zero (CH-11). Pitfall: after 30 days without reports a removed domain's row showed 0% DMARC pass in failure colour (#415, issue #412). The note then went through three wording passes (superscript next to the domain name, a shorter tooltip, mailcow dropped from it), and #434 put "Not on server" beside the domain on phones. Some Dashboard cards showed a made-up value such as 0% when their source did not answer, until #481 made them say Unknown. v3: app.js:2817-2828, 2849, 2884, 4645-4650; dmarc.js:34, 42, 256-264, 554-560, 778.

- **FB-10 Needs attention: only what needs a decision, each with its action.** The Dashboard and Status open with only what needs a decision, each row with a `4px` colored bar, text and its one action: mailcow not reachable (Open settings), a host on a blocklist (Check listing), stopped containers (Ignore, Open status), failed jobs (Run now), Fail2ban entries an earlier version wrote as whole /32 networks (Open lists; "A Fail2ban entry blocks the whole <network> network", "N Fail2ban entries cover whole /32 networks"), DMARC issues (Open DMARC), updates (Read changes), unacknowledged security alerts (Show activity, Dismiss). - **FB-12 Click to copy wherever a value is shown.** IDs, addresses, IPs, usernames, queue and message IDs, DNS records and names copy on a click wherever they appear (tooltip "Click to copy"). - **FB-14 Tones follow meaning.** Use one tone map per domain concept for tags, dots and edges: delivered and sent green, deferred amber, bounced and rejected red, spam its own color, anything else neutral; direction tags keep their own colors (inbound indigo, outbound blue, internal teal) as dots in facets and tags in lists. - **FB-16 Act at once and offer Undo, backed by a server receipt.** An action the server can take back acts on one click and offers Undo instead of asking first (other one-click actions such as Hold and Unhold act without Undo, and DS-20 lists what still asks first): the server answers each change with a receipt for exactly what it changed, and Undo reverts by that receipt only what is still in the state that change left. In v3, Dismiss and Dismiss all in Needs attention (and Dismiss in the alert window) work this way: a success toast "Alert dismissed" or "3 alerts dismissed" with Undo for `10000ms`, longer while the pointer or the keyboard is on it (`offerAlertUndo`). Each dismissal is one update that stores its receipt on the alerts it closed (`ack_batch`) and answers `{acknowledged, ids, receipt}`; `POST /api/security-alerts/acknowledgements/{receipt}/undo` re-opens only alerts still closed by that receipt. Dismiss all sends the ids the list had (`unacknowledged_ids`, read in the same `REPEATABLE READ` snapshot as the rows, up to `10000`), so an alert that arrived later stays open, and its button names the count ("Dismiss all 3 alerts", "Dismiss 1 alert"; a panel under `360px` wide drops the last word, the `aria-label` keeps it). A dismissal that changed nothing (another tab did it) says "Already dismissed" with no Undo; an old Undo cannot re-open an alert dismissed again since ("Nothing to undo: dismissed again since"); a done Undo says "3 alerts back in Needs attention"; a failed Undo says "Could not undo: <reason>." and offers Retry until closed; an Undo whose list does not reload offers Refresh until closed. Keyboard: Undo is named for what it restores (`aria-label` "Undo dismissing <alert>" or "Undo dismissing 3 alerts"); after Undo on the Dashboard the keyboard goes to the first restored alert's Dismiss, else to Needs attention; Undo from another page leaves the keyboard on the message. Pitfall: Dismiss could not be taken back, and Dismiss all could also dismiss an alert that arrived after the list was shown; #480 gave every dismissal a receipt for Undo and made Dismiss all send the ids of the list it was shown with. v3: `offerAlertUndo`, `undoAlertDismissal`, `offerAlertsRefresh`, `showToast(..., { action, duration })`; app.js:1999-2022, 2664-2735; alert-activity.js:294-299; index.html:601; ui.css:1328.
