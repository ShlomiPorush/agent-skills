# UI behavior rules (v3 style): Email

Part of the `v3-ui-style` skill. Companion to `references/v3-design-principles.agents.md` (look, behavior principles, interaction rules, what not to copy). The skill's SKILL.md maps ID prefixes to area files. Paths are relative to the skill folder.

How to read:

- One bullet is one behavior with a stable ID (`DS-1`). A rule may name rules of other areas by ID; when your screen uses that part, read those rules too.
- **Pitfall** marks a behavior whose history shows a failed earlier attempt, a revert or a fixed bug. It says what went wrong and what fixed it. Do not skip it: it is the reason the behavior is shaped the way it is.
- `v3:` gives the v3 helper and `file:line` in the bundled code under `references/v3-code/`, a copy of the mailcow Logs Viewer frontend at commit `0210d15` (`ui.css` is under `assets/css/`). Start at the cited lines and widen to the whole function and what it calls when the bullet is not enough. The rules were first written against the earlier snapshot `deb075d`, then checked rule by rule against this code.
- Rules the interaction fixes changed (October 2026) start with what v3 does now and name its helpers; the part marked "Before the interaction fixes" describes the code before them. Where the two differ, the first part is the rule; details the first part does not cover still hold.
- The principles file's section "Interaction rules v3 follows since its interaction fixes" lists what those fixes added. Never copy anything listed there under "Do not copy".

## Email

- **EM-1 One email layout in the app language.** Every notification email calls one shared layout in the app's language: app icon, name and date on top, a topic tag, a title that says what happened, panels, tables and figures, what to do, and a footer that says where the alert is set. Support light and dark mode and phones, and still send the plain-text part. The layout escapes every value it is given. The header icon travels inside the email as an inline image (`cid:app-icon`), so no client loads anything from the internet.
- **EM-2 Outlook for Windows needs table-only layout.** The email looks right in Outlook for Windows (Word engine) too: spacing is cell padding and spacer rows; divider lines are 1px rows; the topic tag is a table cell; each row of figures is its own table; Outlook gets Segoe UI and a plain square as the app mark; the email is wrapped in a 600px table for Outlook; panels, banners and cards stay square there and only the fixed-size topic tag is rounded with VML; values Word cannot wrap (DKIM keys) are shortened in the middle in the HTML and full in the plain text; an empty 1px row closes the table of cards. Pitfall: Outlook ignores max-width, and Word ignores padding outside table cells, margins, uneven cell borders and font fallbacks; VML rounded panels failed twice (VML inside VML made Word reject the table, and growing VML shapes did not push the next block down, so cards, banners and the footer overlapped), and Outlook drops the bottom border of cells in the last row of a table. Every step was found by sending all 12 emails to Gmail and Outlook for Windows; test with real sends (#419).
- **EM-3 Long lines break tags in transit: send base64.** HTML emails arrive intact with no tag showing as text: send text and HTML parts as UTF-8, base64 encoded (or quoted-printable) for generated HTML. Pitfall: the parts were sent as 7bit with lines of several thousand characters; SMTP allows 998, so the mail server broke lines in the middle of a tag and Gmail showed '< /table>' as text. #419 added a test on the line length that failed on the old code with an 8,522 character line.
- **EM-4 Addresses keep the text color.** Addresses in emails keep the color of the text around them instead of a client's blue link: wrap addresses in links with an explicit color equal to the surrounding text. Pitfall: splitting addresses around the @ so they were not links still failed, because Outlook links them anyway and ignores `color:inherit` (#419). The address-finding pattern runs over text from inbound mail, so it was rewritten without backtracking (#421).
- **EM-5 Subjects say what happened, without emoji.** Subjects name the event and object in plain words, without emoji (blacklist, weekly summary and DMARC import error subjects changed); the weekly failure-rate figure is labelled Failure rate instead of Rating (#419). Pitfall: mail filters on the old subjects need the new ones, so note the change in the changelog.
- **EM-6 One email to several recipients; dates follow the app.** Parse recipient lists once (separated by commas, semicolons or spaces), validate each, and send one email to every configured address (Admin Email, Blacklist Alert Email, Report Import Error Email, the weekly summary, Test SMTP). An invalid entry set through ENV is skipped with a warning so the app still starts and sends to the valid addresses. Emails write dates as day/month/year in the app's time zone, like the dates in the app: the `tz` setting (`TZ` in the environment or Settings > Application; UTC when empty or unknown), and a time carries the zone's short name after it ("20/10/2026 13:00 CET"). The weekly summary title gives the exact window it counts and names the zone once, or at both ends when daylight saving changed in between.
