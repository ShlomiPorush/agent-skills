# UI behavior rules (v3 style): Dialogs and sheets

Part of the `v3-ui-style` skill. Companion to `references/v3-design-principles.agents.md` (look, behavior principles, interaction rules, what not to copy). The skill's SKILL.md maps ID prefixes to area files. Paths are relative to the skill folder.

How to read:

- One bullet is one behavior with a stable ID (`DS-1`). A rule may name rules of other areas by ID; when your screen uses that part, read those rules too.
- **Pitfall** marks a behavior whose history shows a failed earlier attempt, a revert or a fixed bug. It says what went wrong and what fixed it. Do not skip it: it is the reason the behavior is shaped the way it is.
- `v3:` gives the v3 helper and `file:line` in the bundled code under `references/v3-code/`, a copy of the mailcow Logs Viewer frontend at commit `72e43c4` (`ui.css` is under `assets/css/`). Start at the cited lines and widen to the whole function and what it calls when the bullet is not enough. The rules were first written against the earlier snapshot `deb075d`, then checked rule by rule against this code.
- Rules the interaction fixes changed (October 2026) start with what v3 does now and name its helpers; the part marked "Before the interaction fixes" describes the code before them. Where the two differ, the first part is the rule; details the first part does not cover still hold. A sentence that starts "Before the auto-refresh layer" or "Before #509" describes older code in the same way: history, not the rule.
- The principles file's section "Interaction rules v3 follows since its interaction fixes" lists what those fixes added. Never copy anything listed there under "Do not copy".

## Dialogs and sheets

- **DS-1 Phone sheet opens at four fifths and grows with the scroll.** On phones (`max-width: 760px`) every centered dialog, and every help or release-notes text, opens as a bottom sheet with rounded top corners at `max-height: 80vh; max-height: 80dvh`. Scrolling the content first raises the sheet by exactly the scrolled distance, smoothly, until it fills the screen; only then does the content scroll: on each scroll `grow = min(body.scrollTop, innerHeight - panelHeight)`, add `grow` to the panel height and subtract it from `body.scrollTop` so the text stays visually still, ignore growth under 1px. At full height square the corners and clear the notch (`border-radius: 0; padding-top: env(safe-area-inset-top); transition: border-radius .2s ease`). The head keeps its size (`flex-shrink: 0`; the message details scroll their header and tabs inside the body, DS-14), the body gives way (`flex: 1 1 auto; min-height: 0`). Catch every inner scroller (body, tab panel, nested list) with one passive capture-phase scroll listener on the backdrop. Wide screens keep the centered dialog. One dialog opens at full height instead: the container log, which opens at the end of its log and follows it (`uiDialogSheetFull` before its first load, LD-2). Pitfall: the first version jumped to full screen on any scroll; growing by the scrolled amount fixed it (#353), and #428 moved the start from three quarters to four fifths and made every dialog a sheet so phones have one kind of popup. Use `dvh` with a `vh` fallback; create the dialog watcher only where `MutationObserver` and `document.body` exist, because tests load the script without a page. v3: `uiSheetShow(id, { expand: true })`, `uiDialogSheet`; utils.js:1834-1849, 2529-2555, 2646-2662; ui.css:913-916, 3105-3125; app.js:6405-6417.
- **DS-2 Bottom sheet primitive.** A panel rises from the bottom over a `rgb(0 0 0 / .4)` veil, sized to its content up to `max-height: 88vh; max-height: 88dvh`, `border-radius: 16px 16px 0 0`, shadow `0 -8px 30px rgb(0 0 0 / .2)`, layer `position: fixed; inset: 0; z-index: 70` with `justify-content: flex-end`. Grip and head stay fixed; only the body scrolls (`overflow-y: auto; overscroll-behavior: contain; padding: 12px 16px calc(20px + env(safe-area-inset-bottom))`), so reaching its end never scrolls the page behind. Inside, long words wrap (`overflow-wrap: break-word`), `pre` and tables scroll sideways in place (`display: block; max-width: 100%; overflow-x: auto`) and images shrink (`max-width: 100%; height: auto`). Screen reader: panel `role="dialog" aria-modal="true" aria-label`, grip `aria-hidden`, close button `aria-label="Close"` with the shared X icon (`UI_CLOSE_ICON`, DS-24). v3: `uiSheetShow(id, { label, head, body, expand, progress, onClose })`, `uiSheetDismiss(id)`, `uiSheetClose(id)`; utils.js:1804-1859, 845-846; ui.css:908-933.
- **DS-3 Drag to grow, pull down to close, with spring back.** Dragging the grip or the fixed top part (the head; the message details keep their header and tabs inside the body) upward lifts the sheet with the finger toward full screen (`height = min(innerHeight, startHeight - moved)`, `transition: none` during the drag so it tracks 1:1). Pulling down moves it with the finger; released past `min(120px, panelHeight / 4)` it slides off (`transition: transform .2s ease; translateY(100%)`, dismissed after 200ms), released earlier it springs back with the same `.2s ease`. From inside the content a downward pull moves the sheet only when the content and every scroller between the finger and the sheet is at its top (any ancestor with `scrollTop > 0` cancels the gesture); an upward drag from the body never grows the sheet. A touch that starts on a zoomable chart (`[data-zoom]`), or a second finger, never moves or closes the sheet until every finger is lifted (CH-9). All touch and scroll listeners `{ passive: true }`. Touch only: with a mouse the sheet does not drag, and backdrop, X and Escape still close it. Pitfall: a pull from the content must not fight the content's own scroll. A dialog closes only through one of its own buttons, so the owner's cleanup and its Back history entry run: the X in the head (`aria-label="Close"`), or for a question, which has no X, the Cancel in its foot (`[data-cancel]`, `[id$="-cancel"]`), so a pull down cancels a question (DS-12). A button that is off counts as none (the GeoIP setup's X while the setup runs, DS-22): a pull down does not move the sheet, though a drag up still grows it. A dialog with neither can grow but cannot be pulled shut. A pull on a dialog with typed changes presses its X, which asks before it drops them (DS-9). Reset the transform after closing so the dialog reopens normally (#351, #428). Before #509 a question had no Close button, so it could not be pulled shut. v3: `uiSheetSwipe`; utils.js:1908-1943, 2557-2634, 2564-2570.
- **DS-4 Grip: small line, large hit area, bolder while held.** A short line at the top of every sheet: drawn `40px x 4px` in `--ui-line` (centered gradient) inside a `120px x 20px` hit area with `margin-bottom: -4px`. While a finger holds the grip or the fixed head it becomes `56px x 5px` in `--ui-ink` (`transition: background-size .15s ease`) and returns when released: add `.is-held` on `touchstart`, remove it on `touchend` and `touchcancel`. Cursor `grab` and `grabbing` on desktop. Decorative: `aria-hidden="true"`, no keyboard role. Pitfall: the plain handle was too small to catch; #428 added the large hit area and the held state. Without `touch-action: none` on the grip the browser takes the drag for a page scroll. v3: `.ui-sheet-grip`, `.ui-dialog::before` with `.ui-dialog.is-held`; utils.js:1828, 1909, 1915, 1931; ui.css:917-920, 3111-3113.
- **DS-5 Reading gauge in the popup header.** In an information sheet or dialog (help, changelog, release notes) the whole top area, grip plus head, fills from the start side with a faint accent tint as the reader scrolls: empty at the top, full at the end. Width `scrollTop / (scrollHeight - clientHeight) * 100%`, capped at 100; height `head.offsetTop + head.offsetHeight`, measured on each update; fill `color-mix(in srgb, var(--ui-accent) 16%, transparent)`, `transition: width .08s linear`. Hide it when the scrollable room is 1px or less, so a text that does not scroll shows no gauge. The host gets `position: relative; isolation: isolate` so the bar sits at `z-index: -1` behind the head content but not behind the panel; bar `position: absolute; inset-inline: 0; top: 0; overflow: hidden; pointer-events: none`, inheriting the top corner radii. Recompute once more on the next animation frame after opening; attach one listener per scroller. `aria-hidden="true"`; `inset-inline` makes it fill from the right in RTL. v3: `uiReadProgress(headEl, scrollerEl)`, `uiSheetShow(..., { progress: true })`; utils.js:1861-1887; ui.css:3135-3141; app.js:6050-6057.
- **DS-6 Every opening starts fresh; closing cleans up.** Each time a dialog or sheet opens it starts at the top of its content (on a phone at 80% again), on its first tab, never where a previous text was left; the one exception is the container log, which opens at the end of its log (on a phone at full height, LD-2). On each opening of a phone dialog sheet clear the inline height and transform, scroll every `.ui-dialog-body` to 0 and remove `is-grown`/`is-full`; attach its listeners once (`data-sheet`). For a shared info dialog set `body.scrollTop = 0` after `classList.remove('hidden')`. Closing clears what belonged to that opening: the open item key, the selected row mark, the scroll lock, pending searches and late answers. Example: Manage Reports resets search and sort on every opening, and on close cancels its search timer and dim and bumps its request counters so late answers cannot repaint a closed dialog. Pitfall: help, changelog and update notes share one dialog, and each opened with the new text but kept the scroll position of the one before, so a help page could open in its middle (#374); #428 made every phone sheet start at the top. A hidden element cannot be scrolled, so reset after it is shown. v3: utils.js:2535-2541; app.js:6405-6411; app.js:6048-6056; message-details.js:54, 132-161, 1340; dmarc.js:1304, 1461.
- **DS-7 A redrawn sheet keeps its place.** When a page redraws an open sheet with new data it does not jump to the top or shrink: restore the previous `.ui-sheet-body.scrollTop`, and keep a grown height in `sheet.dataset.height` and reapply it, so a sheet the user grew stays grown. The sheet stays open through the page's own refresh. Drawn again with the same content (`sheet.dataset.shown` holds what it showed), or while text in it is selected (`uiTextHeld`), it is left as it is, with its focus, selection and scroll; drawn with new content, the focus goes back to the same control (same tag and the same `aria-label` or text, SV-13). Example: the Security address sheet redraws on the page's 30-second refresh only when the address changed, and closes by itself when the address leaves the list. v3: `uiSheetShow` called again with the same `id`; utils.js:1802-1833, 1838.
- **DS-8 Escape closes the top layer only.** One owner decides: a window-capture Escape handler (router.js) closes only the top layer, ordered by z-index and then page order, through its Close or Cancel button, and stops the event, so no listener of a layer underneath sees it. It yields to a picker or an open popover inside the top layer and to the phone search, which close themselves. No dialog has its own Escape listener; the docked reading pane, which is not a layer, still closes on Escape when no layer is open. Focus moves into a layer when it opens (its first field, but not on a touch screen, where it would raise the keyboard; else its primary button; else the panel), returns to the control that opened it (a window that opens after a request names its opener before the request), and falls back to the layer below or the page heading. Everything beside the path from the page to the top layer is `inert`, except toasts and, beside the phone More sheet, the tab bar; `aria-modal` is set only while the element is a layer. Every layer closes this way, through its own Close or Cancel: confirmations, the record window, alert activity, the message dialog, sheets. A picker's Escape (capture phase) closes only the picker and returns focus to its button; an open row menu closes on the native popover's Escape. Back follows DS-10. Helpers: `openOverlays`, `closeTopOverlay`, `layerChildOwnsEscape`, `syncLayerFocus`, `uiLayerOpener` in router.js. Before the interaction fixes (history; where it differs from the text above, the text above is the rule): Escape closes only the topmost thing: an open picker inside a dialog closes before the dialog, the global search closes without closing a dialog under it, and with several sheets the last `.ui-sheet` in DOM order closes. Confirmations, the record window, alert activity and sheets all close on Escape. Nested layers listen in the capture phase and call `stopPropagation` (the picker's keydown in the capture phase, the search with `stopPropagation`); the confirm has its own listener; row menus use the native popover's Escape; Back follows DS-10. A picker's Escape returns focus to its button. Pitfall: before #431 the Messages pickers did not close on Escape; #431 listens in the capture phase "so Escape closes the picker before it reaches a dialog or sheet under it". #278 made the shared confirm close on Escape, and #385/#387 did the same for the record window. v3: router.js:328-375, 392-516; utils.js:2939-2957, 928-929; search.js:595-599.
- **DS-9 Backdrop and close rules per dialog kind.** The rule holds for every window: a click outside closes a window without typed input (the container log, the Changelog, rule test results, quarantine details, alert activity, mailbox activity, the DMARC record, fetch history, a connection test, Block details, the GeoIP setup once it has finished, a confirmation as Cancel) and never one with typed input (Basic Auth verification, Manage Reports with its search, every edit dialog). A dialog built by `uiDialog` gets the click outside only when it passes `backdropClose` (DS-24), so a window with typed input never gets it by accident. A click outside counts only when the press started on the backdrop too: every backdrop closer asks `uiBackdropClick(event)`, which is true when `event.target` is the backdrop and the last press (`uiPress`, recorded by a capture-phase `mousedown` listener) started on it; a click with no mouse (`detail` `0`) or with no press recorded passes. So a drag that selects text in a dialog and is released on the backdrop leaves the dialog open with the text selected, and a plain click on the backdrop still closes it. A press ends on `mouseup`, on a `mousemove` with no button down, or when the window loses focus (`blur`), so a release outside the window never leaves it held. A click inside a dialog never closes it, because its target is not the backdrop; no closer compares `event.target` by itself. Clicks inside a dialog reach the page's own handlers, so its drop-downs (`uiPicker`) open and close there; no dialog stops propagation from `.ui-dialog`; the suppression add and edit dialogs have no backdrop handler and are removed from the DOM on close. A typed dialog (quarantine rule, notification destination, suppression add and edit) asks "Discard your changes?" with [Keep editing] then [Discard] on screen, focus on Keep editing, when its X, Cancel, Escape, Back or a pull down on a phone would drop a field that differs from how it opened (the suppression dialogs' X goes through `uiCancelDialog`, as their Cancel does); a save closes it without asking and closes a question still open for it. A connection test window is one at a time, and a reply for a closed or older test is dropped. A sheet closes on a backdrop tap, X or Escape, and the page that opened it can run its own close logic: `onClose` replaces the default removal and usually ends with `uiSheetClose(id)`. Helpers: `uiGuardDialog`, `uiCloseGuarded`, `uiCancelDialog`, `uiDialogSaved`, `uiBackdropClick` in utils.js. Before the interaction fixes (history; where it differs from the text above, the text above is the rule): Windows that show information close on a backdrop click and on Escape; small edit dialogs with typed input stay open on a backdrop click and close by Cancel or X; a click inside a dialog never closes it. Backdrop handler `onclick="if (event.target === this) close...()"` on alert activity, mailbox activity and DMARC record, backdrop close also on fetch history and Manage Reports; Escape on DMARC record, mailbox activity and message details; the message dialog stops propagation from `.ui-dialog`; suppression dialogs use `onclick="event.stopPropagation()"`, have no backdrop handler and are removed from the DOM on close. A sheet closes on a backdrop tap or X, and the page that opened it can run its own close logic: `onClose` replaces the default removal and usually ends with `uiSheetClose(id)`. Pitfall: selecting text in a dialog and releasing the mouse on the dark area around it closed the dialog, because the browser sends that click to the backdrop; #474 closes only when the press started on the backdrop, in every backdrop closer. Before #509 Add and Edit Suppression, Block details, the GeoIP setup and Verify credentials had no X, and the suppression dialogs stopped clicks from leaving `.ui-dialog`. v3: `uiBackdropClick(event)`, `uiPress`, `uiSheetShow(..., { onClose })`, `uiSheetDismiss(id)`, `uiDialog({ backdropClose })`; utils.js:888-889, 1002-1014, 1488-1500, 1511-1518, 929, 963, 974-1014, 1826, 1829, 1889-1901; index.html:1529-1530, 1581, 1596, 1631; app.js:4131-4138, 4672-4684, 4523-4531, 6059-6069, 6231-6247; dmarc.js:752-754, 1236-1242, 1304-1306; mailbox-stats.js:512-514; message-details.js:1359-1370; settings.js:168-170, 2322-2331, 2856-2864; spam_filter.js:780-791, 818-822.
- **DS-10 Back closes the top overlay instead of leaving the page.** With a dialog, a sheet (phone help, an address), the container log, the phone More menu or the phone search open, the browser Back button or phone back gesture closes the top one and stays on the page; with two overlays each Back closes one, and a jump of several steps back closes every open one. While anything is open hold one extra history entry at the same URL with `state.overlay = true`, kept in sync by a body `MutationObserver` (class changes and added nodes) batched per animation frame; a layer marked `data-no-history` (the "Leave without saving?" question, which is also asked during Back and Forward) adds none. To close the top overlay look in it for `[aria-label="Close"]`, `[id$="-cancel"]`, `[data-cancel]`, a button whose text is Cancel/Close, a button whose `onclick` starts with `close`, else send a synthetic Escape; the More menu uses `closeMobileMenu()`. Give each overlay such a Close button so Back runs its own close logic (the confirm is cancelled by Back through `#app-confirm-cancel`, a choice dialog through `[data-cancel]`, and a typed dialog asks first, DS-9). Closing by hand calls `history.back()` and ignores the resulting popstate, so the next Back really leaves the page; navigation from inside a dialog replaces the overlay entry (`routerReplace`, `replaceState`), so no stale dialog step is left behind. Order the open layers by z-index, then page order (DS-8): the phone search drops below a message it opened, so the message counts as on top; exclude `.ui-dialog-backdrop.ui-docked`. Pitfall: on a phone, Back with a message open went to the previous page and left the message behind (#312), and Back left the page behind the full-screen phone search instead of closing it (#383). Overlays open by class change or by insertion, so watch both, and decide the stacking order explicitly. v3: `OVERLAY_SELECTOR`; router.js:299-546, 278-286, 310-312, 317-332, 528-534, 647-675, 710-714.
- **DS-11 Scroll lock behind overlays.** While a dialog or sheet is open the page behind stays still: `body.ui-sheet-on { overflow: hidden }`, released only when the last sheet closes; dialogs set `document.body.style.overflow = 'hidden'` and restore `''`; a question (DS-12) keeps the value it found and puts it back, so a question asked from a dialog leaves the page locked until that dialog closes. In an app-frame layout lock every scroll region, not only body: with Message Details open as an overlay, `html:has(#message-modal:not(.hidden):not(.ui-docked))` sets `overflow: hidden !important` on html, body, `.ui-page`, `.ui-scroll`, `.ui-gs-body`, `.ui-sidenav`. The dialog's own scroll never chains outward and its last line clears the phone home bar: dialog sheet body `overscroll-behavior: contain; padding-bottom: calc(var(--ui-pad-x) + env(safe-area-inset-bottom))`. Keep that inset on whatever element scrolls: a dialog with a foot clears the home bar in its foot instead (`padding-bottom: calc(12px + env(safe-area-inset-bottom))`, the body keeps `var(--ui-pad-x)`), and the message details, which scroll inside `.ui-md-content`, put the inset there (`#message-modal:not(.ui-docked) .ui-md-content`). Before #509 the message details sheet lost it, because its scroller's `padding: 0` (`#message-modal .ui-md-body`) won over the sheet rule (ui.css:491, 3054 at 8caf6e43). A dialog blocks the page behind it; a docked reading pane does not. v3: `uiSheetShow` handles `ui-sheet-on`; utils.js:1857, 1900, 917, 925; ui.css:939, 2855-2859, 3119, 3121-3124.
- **DS-12 Styled confirmation dialog.** Destructive or important actions ask in a small fitted in-app dialog (`uiDialog` with `role: 'alertdialog'` and `size: 'sm'`, DS-24) with a title, a message and two buttons instead of the browser's confirm(); newlines in the message become line breaks, the text is escaped, and a second confirm replaces the first. The confirm button takes focus after `100ms`, so Enter confirms; Escape (through the layers, DS-8) and a click outside cancel (resolve false). A question that protects changes ("Leave without saving?" [Stay] [Leave], "Discard your changes?" [Keep editing] [Discard]) starts on its safe answer instead (`focusCancel: true`), and the Leave question writes no history entry of its own (`noHistory: true` sets `data-no-history`), since it is also asked during Back and Forward. A dangerous action (`isDangerous: true`) gets a solid red `ui-btn-danger-solid` button, otherwise `ui-btn-primary`, with optional `confirmColor`. A question with more than two answers uses the same frame through `showChoiceModal`: Cancel first, then one button per choice (`kind` primary, danger or plain), focus on Cancel after `50ms` so Enter never picks a destructive choice, Cancel, Escape and a click outside resolve `null`, and a second one closes the first as cancelled (example: "Keep this app's Rspamd blocks?" [Cancel] [Keep blocks] [Remove blocks]). It appears above any dialog it was opened from with only toasts above it (`.ui-dialog-backdrop.ui-confirm { z-index: 99999 }`, toasts at `100000`) and locks the page (`body.style.overflow = 'hidden'`), then gives back the value it found, so a question asked from a dialog leaves the page locked (DS-11). It has no X; on phones it is a sheet, and a pull down cancels it as its Cancel does, as Back does (`#app-confirm-cancel`, `[data-cancel]`, DS-3). Enter on its Cancel presses Cancel. A question built by its own code (Disable features) confirms on Enter only when the focus is not on a button. Screen reader: `role="alertdialog"`, `aria-label=<title>`, `aria-modal` set by the layers; the choice dialog also has `aria-modal="true"` and `aria-describedby` on its message. Example: settings use `role="alertdialog"` for disabling a feature and `role="dialog"` for verifying credentials. Pitfall: the confirm was always dark whatever the theme; #278 made it follow the theme and close on Escape. Before #509 a question could not be pulled shut, and Enter on the Cancel of Disable features deleted the data. v3: `await showConfirmModal({ title, message, confirmText, cancelText, confirmColor, isDangerous, focusCancel, noHistory })` resolves true or false; `await showChoiceModal({ title, message, choices: [{ value, label, kind }], cancelText })` resolves the chosen value or null; utils.js:894-968, 1069-1083; ui.css:2408, 2394; settings.js:57-59, 143-145, 164-166, 714-718; utils.js:907-929, 2564-2570.
- **DS-13 Docked reading pane on wide screens, dialog elsewhere.** On the Messages page on a wide screen (`matchMedia('(min-width: 1000px)')` matches and `currentTab === 'messages'`) a message opens as a third column beside the list, like a mail client: no dialog head, no shadow, the clicked row highlighted, and the first message opens by itself when the list loads (when a reader slot exists, the dialog is hidden and the list is not empty). Everywhere else, and on narrower screens, the same element is a dialog and the page behind is locked. Docked form: `#message-modal.ui-docked { position: static; display: block; height: 100% }`, dialog `border: 0; border-radius: 0; box-shadow: none`, head hidden, header padding `30px 36px 0`, content `20px 36px 60px` (on `.ui-md-content`; the body has no padding); hide the "Select a message" hint with `.ui-reader:has(#message-modal:not(.hidden)) .ui-reader-empty`. Use one element that moves between forms so every id and handler stays; as a dialog it moves to the end of body, so it opens over any dialog already open (Block details opens a message from its own dialog) and Escape closes the message first, and exclude docked dialogs from sheet, drag, scroll lock and Back history logic. Auto refresh keeps running while docked and pauses while it is a dialog. Pitfall: #261 paused auto refresh whenever a message was open "so the list does not re-render under the reader"; #268 kept it running for the docked form (a dialog still pauses it) and opened the first message in the pane. v3: `.ui-docked`, `messageReaderSlot`, `placeMessageModal`; message-details.js:19-42, 109-112; spam_filter.js:785-786; app.js:5016-5025; ui.css:623, 625-633, 2856-2858; utils.js:2542; router.js:310-312.
- **DS-14 Sticky heads inside a scrolling dialog stick at the visible edge.** A message's details scroll as one: the dialog body (`#message-modal-body`, classes `ui-dialog-body ui-md-body`) holds the header (subject, From, To, When, outcome), the tabs and the open tab (`#message-modal-content`), so no number of recipients can push the logs out of reach. The tabs stick at the top of that scroller and the Logs tab's timeline head (title, count, Recipient picker, source chips) sticks right under them, with no log line peeking above, in the dialog, the phone sheet and the docked pane: scroller `padding: 0`; tabs `position: sticky; top: 0; z-index: 6; background: var(--ui-bg)`; content `padding: var(--ui-pad-x)` (docked `20px 36px 60px`); timeline head `position: sticky; top: 0; z-index: 2; padding: 6px 0; background: var(--ui-bg)`, in the message `top: var(--ui-md-tabs-h, 41px); z-index: 5`, where `--ui-md-tabs-h` is the tabs' measured `offsetHeight`, set when a message opens; a part a link jumps to stops under the tabs (`scroll-margin-top: calc(var(--ui-md-tabs-h, 41px) + 8px)`); `.ui-md-fill:has(.ui-md-timeline) { height: auto }`. Each message opens at its top (`scrollTop = 0`); a tab switch while scrolled past the header sets `scrollTop` to the header's height, so the new tab starts right under the tabs. Opening the Recipient picker first scrolls the timeline head up to the tabs when it sits more than `1px` below them, so its list opens downward; while its panel is open the head rises over the tabs (`z-index: 7`) in case it must open upward. Put a scroller's padding on its content, not on the scroller, so sticky `top: 0` is the visible edge. Pitfall: the message body scrolled with top padding, so the sticky head stopped below it and log lines showed through above the head (#291); a scrolling container's top padding offsets every sticky child by that padding. The header listed every recipient above the tabs, outside the scroll, so from about 20 recipients the Logs tab had no room left and the timeline could not be reached, worst on phones; #483 made the header, the tabs and the tab one scroller with the tabs pinned. v3: `measureMessageTabs`, `switchModalTab`, `mdRecipientPickerOpen`; index.html:1489-1503; message-details.js:54-91, 118-120, 788-797; ui.css:490-503, 630-633, 3192.
- **DS-15 Dialogs live at body level.** A dialog is never hidden behind page content or sticky bars: append dialogs to body, outside the app content (the container log dialog sits outside `#app-content` as a child of body, a `.ui-dialog-backdrop` like every other dialog; before #509 it was a Tailwind `fixed inset-0 z-50` box of its own). Pitfall: the container log dialog lived in the sidebar, whose sticky position made a stacking context, so the sticky Settings search showed above it (#290); `position: sticky` creates a stacking context, and a dialog inside it cannot rise above other sticky content whatever its z-index. v3: index.html:1527-1540; utils.js:890.
