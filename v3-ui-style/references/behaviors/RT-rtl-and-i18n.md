# UI behavior rules (v3 style): RTL and i18n

Part of the `v3-ui-style` skill. Companion to `references/v3-design-principles.agents.md` (look, behavior principles, interaction rules, what not to copy). The skill's SKILL.md maps ID prefixes to area files. Paths are relative to the skill folder.

How to read:

- One bullet is one behavior with a stable ID (`DS-1`). A rule may name rules of other areas by ID; when your screen uses that part, read those rules too.
- **Pitfall** marks a behavior whose history shows a failed earlier attempt, a revert or a fixed bug. It says what went wrong and what fixed it. Do not skip it: it is the reason the behavior is shaped the way it is.
- `v3:` gives the v3 helper and `file:line` in the bundled code under `references/v3-code/`, a copy of the mailcow Logs Viewer frontend at commit `72e43c4` (`ui.css` is under `assets/css/`). Start at the cited lines and widen to the whole function and what it calls when the bullet is not enough. The rules were first written against the earlier snapshot `deb075d`, then checked rule by rule against this code.
- Rules the interaction fixes changed (October 2026) start with what v3 does now and name its helpers; the part marked "Before the interaction fixes" describes the code before them. Where the two differ, the first part is the rule; details the first part does not cover still hold. A sentence that starts "Before the auto-refresh layer" or "Before #509" describes older code in the same way: history, not the rule.
- The principles file's section "Interaction rules v3 follows since its interaction fixes" lists what those fixes added. Never copy anything listed there under "Do not copy".

## RTL and i18n

- **RT-1 Logical properties and mirrored controls.** Use logical properties only, so start and end padding, insets, borders, badges, popovers and the reading gauge mirror for right-to-left: `margin-inline-start`, `inset-inline-start/end`, `border-inline-start`, `padding-inline-*`, `border-start-*-radius`, `text-align: start/end` (toast `inset-inline-end`, sort arrow `margin-inline-start`, search panel `inset-inline: 0`). Mirror icons and keys under `[dir="rtl"]`: switch knobs slide the other way (`translateX(-16px)`), the domain chevron points left (`.ui-domain-chevron { transform: scaleX(-1) }`), row menus align to the button's left edge from its computed `direction`, the active search result bar and the chosen network row's bar sit on the right (`.ui-gs-item.is-active`, `.ui-sec-net.is-on`: `box-shadow: inset -3px 0 0 ink`), and the sidebar's page flyout opens on the sidebar's other side and slides in from it (`[dir="rtl"] .ui-fly { transform: translateX(4px) }`). Charts keep time running left to right in both directions (`direction: ltr` on the DMARC days, the alert history, the mail flow, the overview strip and the DMARC calendar). Keyboard: the search's Left and Right keys swap (`(event.key === 'ArrowRight') !== rtl`), and the flyout's key back to the sidebar is Left, or Right in RTL; the DMARC calendar's Left and Right do not swap, since its time runs left to right. v3: ui.css:158, 333, 350, 576, 817, 873, 1626, 1774, 2145, 2394-2395, 2541, 2609, 2792, 2796, 2811-2812, 2932, 3138-3139; utils.js:406-407; search.js:585-586; app.js:6476-6478, 6504-6505; dmarc.js:420-434.
- **RT-2 Mixed-direction user text with dir="auto" and bdi.** Put `dir="auto"` on every element holding user-supplied text that may be right-to-left (subjects, rule names, match values, quarantine content, Rspamd history subjects, rate-limit subjects, device names) so it lays out in its own direction inside the page, and wrap copyable emails, IPs and device names in `<bdi>` so they keep their direction inside RTL text. Screen reader: correct bidi reading order. Demo data includes Hebrew and Arabic subjects so this is always exercised. v3: index.html:384-388; utils.js:733; app.js:1434, 3965, 4202, 4223, 4355, 4357, 4651, 4658; message-details.js:913; logs-viewer.js:701; rate-limits.js:617; devices.js:160.
- **RT-3 One UI font for Hebrew, Latin and digits; files downloaded only when used.** Two self-hosted fonts, one `@font-face` per script file with `unicode-range` and `font-display: swap`, so the browser downloads only the scripts a page uses. Noto Sans Hebrew is the whole UI font: its `hebrew`, `latin` and `latin-ext` files (variable, `font-weight: 100 900`), so a digit or an English word in a Hebrew line is drawn in the same design and size as the Hebrew around it; stack `'Noto Sans Hebrew', system-ui, sans-serif`. IBM Plex Mono is only for machine values (IP addresses, hashes, keys, slugs, IDs and ID numbers, domains, one-time codes, log lines); its 500 files are declared for `font-weight: 500 900` so a mono value in bold text keeps its real letters instead of a bold the browser fakes; stack `'IBM Plex Mono', 'Noto Sans Hebrew', ...`. Email addresses, phone numbers and customer codes are text people read and use the UI font, in every component; they keep their own direction (RT-2). Noto Sans Hebrew has no basic Cyrillic or Greek and lacks some extended Latin letters (such as Ə and ŋ), which fall back to `system-ui`; a project whose users or data use them adds a font that covers them after Noto Sans Hebrew and checks real samples. The files and their OFL licences are bundled in `references/v3-code/assets/fonts/`. A test fails if a page loads any external font, script, stylesheet or image. Pitfall: v3 at the bundled commit put a Latin font (Onest) before Noto Sans Hebrew, whose file covered only the Hebrew block, so digits and Latin came from the Latin font and looked foreign and the wrong size in Hebrew text. The bundled `ui.css` carries this rule; the bundled page scripts still show some emails in mono, and this rule wins over them. v3: ui.css:18-66.
- **RT-4 Labels spelled from keys, readable.** One label function spells a setting's readable name from its key, with acronyms in capitals (SSL, IMAP, TLS, OAuth, OIDC, API, URL, IP, DNS, DMARC, SPF, DKIM, SMTP, CSV, ENV, DB), "Rw" as "(read-write)" and a leading "mailcow" lowercase, plus an override map for labels the key cannot spell well ("Report Import Error Email", "Retention Days", "Time Zone") and for the Outbound settings, named for what they do ("Handle undeliverable mail automatically", "Sync with Rspamd", "Permanent delivery failure", "Exclude these domains"); settings shared by DMARC and TLS drop the "DMARC" prefix (IMAP Host, Retention Days). Search still finds them by key. Help titles read as words: `Help - ${title || docName.replace(/_/g, ' ')}`, the page's own name when it passes one ("Help - Outgoing spam" for `Abuse_Protection`), else the file name ("Help - Mailbox Stats" from `Mailbox_Stats`). Pitfall: names "said DMARC only" although they covered TLS reports too, fixed in #339; help titles showed "Help - Abuse_Protection" until #429. v3: `settingsFieldLabel`; settings.js:15-36, 1168-1181; app.js:6299-6300; search.js:110.
- **RT-5 Country names from the browser; flags in a fixed slot.** The country list of the protection rules comes from the browser in the UI language (`Intl.DisplayNames(['en'], { type: 'region' })`); names on log rows come from the server's GeoIP data; the flag shows wherever a country is named; in Security rows the flag sits in a fixed 16px slot (flag 16x12) before the address so every address starts at the same place; a missing flag image hides or removes itself (`onerror="this.style.display='none'"` or `onerror="this.remove()"`) instead of showing a broken icon. Build a flag URL only from a two-letter code. Screen reader: a flag beside the written name `alt=""` (Security rows, events); the GeoIP lines (`renderGeoIPInfo`, `renderGeoIPForDMARC`) use the country name as `alt`. v3: `getFlagUrl`; app.js:1731, 6075-6080, 6106, 6159; security.js:123-127, 422-425; ui.css:846-847; protection.js:92; app.js:6104, 6124.
