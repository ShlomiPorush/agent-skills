# UI behavior rules (v3 style): Live data and logs

Part of the `v3-ui-style` skill. Companion to `references/v3-design-principles.agents.md` (look, behavior principles, interaction rules, what not to copy). The skill's SKILL.md maps ID prefixes to area files. Paths are relative to the skill folder.

How to read:

- One bullet is one behavior with a stable ID (`DS-1`). A rule may name rules of other areas by ID; when your screen uses that part, read those rules too.
- **Pitfall** marks a behavior whose history shows a failed earlier attempt, a revert or a fixed bug. It says what went wrong and what fixed it. Do not skip it: it is the reason the behavior is shaped the way it is.
- `v3:` gives the v3 helper and `file:line` in the bundled code under `references/v3-code/`, a copy of the mailcow Logs Viewer frontend at commit `72e43c4` (`ui.css` is under `assets/css/`). Start at the cited lines and widen to the whole function and what it calls when the bullet is not enough. The rules were first written against the earlier snapshot `deb075d`, then checked rule by rule against this code.
- Rules the interaction fixes changed (October 2026) start with what v3 does now and name its helpers; the part marked "Before the interaction fixes" describes the code before them. Where the two differ, the first part is the rule; details the first part does not cover still hold. A sentence that starts "Before the auto-refresh layer" or "Before #509" describes older code in the same way: history, not the rule.
- The principles file's section "Interaction rules v3 follows since its interaction fixes" lists what those fixes added. Never copy anything listed there under "Do not copy".

## Live data and logs

- **LD-1 Live tail with reconnect and a connection state.** The selected service's log streams in live (token from `/api/raw-logs/ws-token`, then `ws(s)://host/ws/raw-logs?service=<id>&token=...`). A dropped connection reconnects by itself after 3000ms while the user stays on the page and is not paused, but not after an authentication failure (close code 4401 or a server error containing "Authentication"); manual disconnects null `onclose` first. When its session ends (sign-out, expiry, a sign-in settings change) the server closes the stream with code 4001; the page reconnects as after any drop, and the token request then sends it to sign-in. A dot and a word show Connected (green), Paused (amber) or Disconnected (red) (`ui-mdot-ok|warn|fail`), so the state is also in text. Pause stops the stream (the button turns into Resume); lines that arrived while paused are not fetched afterwards. While a loaded time range is shown, new live lines are not added and the stream's counts do not replace the range's total, until Live. The Live button clears any range, reloads the newest lines and reconnects. Leaving the Logs page closes the stream. Keyboard: Pause and Live `aria-pressed`. v3: `connectLogWebSocket`, `disconnectLogWebSocket`, `updateWsIndicator`, `toggleLogPause`, `resetToLiveLogs`; logs-viewer.js:774-959, 1161-1184; app.js:2138-2141.
- **LD-2 Follow the end only when the reader is there.** A live log jumps to the newest line only while the reader is there, and loading older history never moves the view. The container log is a shared dialog with a terminal body (DS-16); on a phone it opens as a full-height sheet at the end of the log (`uiDialogSheetFull` one frame after it shows, since the dialog watcher would undo it earlier, then the first load, DS-1) and follows new lines from there. It shows the last 500 lines and refresh every 2000ms with `silent=true` (no "Loading logs..." flash), with no Refresh button; the refresh replaces the lines only while the reader is at the newest line (`containerLogsAtEnd`: `scrollHeight - scrollTop - clientHeight <= 4`, tested before the request and again on the answer), so scrolling up to read stops it and coming back to the end resumes it; it also skips while text is held in the log (LD-14) and while the browser tab is hidden, and closing stops the polling. On the Logs page following is the Auto-scroll toggle (default on, `aria-pressed`), not a position test: while it is on, every live batch goes to the newest line (bottom, or top in newest-first order). Selecting text in the log (a click on a line or a drag, seen through `selectionchange` and `uiTextHeld`) turns Auto-scroll off and its button shows it; turning it on goes to the newest edge (`scrollTop = 0` in newest-first, else `scrollHeight`) and drops a selection inside the log, which would turn it off again. Live lines that arrive while Auto-scroll is off (not paused, no loaded range) are kept, up to `MAX_LIVE_LOG_ENTRIES = 5000`, for a "N new lines" button ("1 new line") at the newest edge: a sticky pill (`position: sticky; height: 0; z-index: 2`, `30px` high, `border-radius: 999px`, `12px` from the edge) with an arrow down, or up and at the top in newest-first, `title="Go to the newest line and turn auto-scroll on"`. It counts only the lines the current search and quick filters show, recounts when they change and hides at 0; Clear, a fresh render (a service opened, Live, a time range, the order toggle) or a scroll by hand to within `4px` of the newest edge clears it (a `wheel`, `touchmove` or `keydown` on the terminal in the last `1000ms`, or a press on the terminal itself, its scroll bar; the log growing or a filter shrinking it does not). A click on it goes to the newest line and turns Auto-scroll on (`jumpToNewestLogs`). Keyboard: Auto-scroll `aria-pressed`; the pill is a `button`. Pitfall: new lines took a selection away, and turning Auto-scroll back on jumped to the bottom even in newest-first order; #474 turns Auto-scroll off while text is selected, counts what arrives for the New lines button instead, and goes to the newest edge in either order. v3: `setLogAutoScroll(on)`, `toggleAutoScroll`, `jumpToNewestLogs`, `updateLogNewLines`, `uiTextHeld`; app.js:6344-6432, 6405-6417; logs-viewer.js:403-432, 497-500, 557-563, 811-818, 959-1010, 1236-1238, 1279-1280; index.html:1353-1355, 1417-1422; ui.css:2361-2369.
- **LD-3 Newest first or last, remembered; opens on the newest page.** A toggle flips the display order between classic tail (newest at the bottom) and newest at the top, re-renders what is loaded, and is remembered between visits (`localStorage['logsNewestFirst'] = 'true'|'false'`); its label and icon arrow say where the newest line lives. Keep stored entries chronological and reverse only in rendering (the DOM is reversed per batch). Opening a service shows its newest entries, not the oldest: with page size 500 it reads the total, then fetches the last page. v3: logs-viewer.js:20, 286, 504-506, 568-576.
- **LD-4 Scroll back through history without a jump; a capped live buffer.** Scrolling within 50px of the history edge (the top, or the bottom in newest-first) loads the previous page of 500 older lines, with "Loading older logs..." at that edge; a failure shows "Failed to load older logs", which disappears after 3000ms. The view stays on the same line while they are inserted above: measure the height before and after inserting and add the difference to `scrollTop` (`scrollTop = newHeight - prevHeight` when inserting at the top). A busy server does not slow the tab: the oldest live lines drop off past `MAX_LIVE_LOG_ENTRIES = 5000`, but pages loaded on purpose are not trimmed, and no lines are trimmed while the user selects or has selected text in the log (`uiTextHeld`), so the selected lines stay; the next update after that trims the whole excess. v3: `uiTextHeld`; logs-viewer.js:331-400, 403-432, 469, 497-500, 537-548.
- **LD-5 Clear stays cleared.** Clear empties the terminal with "Display cleared. New logs will appear here."; the next live lines replace the note. Scrolling up does not bring history back (`oldestPageLoaded = 1`), and a history request already on its way is dropped: increment a view id (`viewId`) on Clear and check it after every await. Search, quick filters and range are cleared too. Pitfall: Clear used to refill the screen with history; #290 made it stay cleared. v3: `viewId`; logs-viewer.js:367, 482, 1271.
- **LD-6 Log lines colored by meaning, matches marked, filters apply to new lines.** Lines are tinted by meaning per service so problems stand out. Generic: red reject, error, blocked, denied, failed, fatal; yellow warning, pregreet, timeout; green sent, connect from, login, delivered, success; gray disconnect, removed, noqueue. API methods GET green, POST yellow, PUT blue, DELETE red, data cut at 200; watchdog by hpdiff and lvl; Rspamd score red at reject threshold (fallback 15), orange at add header (fallback 8), yellow 0 and above, green below 0, subject cut at 80 (`dir="auto"`); time blue, program cyan. The search term is marked in every visible line (`<mark>`, case-insensitive, regex-escaped). With a search or quick filter active, new live lines that do not match arrive hidden (`display: none` plus `.log-filtered`) and the match count updates; while filtering, a pill in the status bar next to the entry count (`.ui-logs-filter`, the app's filter pill; a long search wraps inside it, so it stays in sight while the lines scroll) says "Showing 12 of 500 - filter: "timeout" + Auth failures", with an X (`aria-label` and `title` "Clear all filters") that clears everything. Each service offers its own colored quick-filter chips (`aria-pressed`) with a description tooltip, matching `pattern` on `program` or `message`; chips combine with OR, search with AND; a service with none hides the row. v3: `formatLogLine`, `entryMatchesFilters`, `updateFilterBadge`, `loadSmartFilters`; logs-viewer.js:190, 270, 435-461, 519-555, 614-736, 1241; ui.css:763-764, 2376.
- **LD-7 Quick filters fold to a row and a half.** Many quick-filter chips fold to about one and a half rows with a fade, so the cut second row shows there is more: fold height `round(rowH * 1.6 + 6)`px, `.ui-chip-row.is-folded { max-height: var(--ui-fold-h, 52px); overflow: hidden; mask-image: linear-gradient(to bottom, #000 55%, transparent) }`. "Show all N" next to the Quick Filters title opens them, "Show less" folds again (toggle `aria-expanded`, `aria-controls`). Fold only if `scrollHeight > foldH + rowH`, that is only when it saves at least a full row; an active chip never hides in the folded part (the row opens instead); where chips fit in two rows nothing folds. A ResizeObserver refits only when the rounded width changes. Pitfall: the link first sat under the folded chips (#313); it now follows the Quick Filters title on the same line (#314). Fold only when it saves at least a row, and refit when the chips get their size (the page was hidden, or the width changed). v3: `fitQuickFilters`, `toggleQuickFilters`, `--ui-fold-h`; logs-viewer.js:221-252; ui.css:2580-2589; index.html:1406.
- **LD-8 Range presets load at once; a custom range sits behind a chip.** The range row shows 1h, 6h, 24h, 48h (60, 360, 1440, 2880 minutes) and a Custom chip. A preset fills From and To and loads at once. Custom reveals a From/To row (`datetime-local` `YYYY-MM-DDTHH:MM`) with Load on its own full line (`.ui-logs-custom { flex: 1 1 100% }`) and puts the cursor in From; with no From nothing happens. The fields hold wall times in the app time zone: a preset writes them there and sends its exact instants while the fields still show them; a typed time is read in the app time zone, and To covers its whole minute. Loading a range fetches every page (page size 1000) with "Loading page 3/7...", keeps Load disabled while loading, switches Live off and re-applies active filters. Keyboard: Custom chip `aria-expanded`, `aria-pressed`, `aria-controls="logs-custom-range"`. v3: `setLogTimePreset`, `toggleLogCustomRange`, `loadDateRangeLogs`, `setLogDateInput`, `readLogDateInput`; logs-viewer.js:260, 1042-1060, 1063, 1075; ui.css:2580-2582; index.html:1387-1399.
- **LD-9 Log service list with counts; switching resets the view.** A side list names each log service with an icon (`aria-hidden`) and its number of entries (1000 and more as `1.2K`), kept current by the live stream; the current one is marked (`aria-current="true"`); the default is `postfix`, else the first. Picking another clears the date range, reloads its quick filters, shows its newest lines and reconnects; on narrow screens the picker folds closed into one row that names the current service and its count. A status bar says "1.5K of 12.3K entries" while only part is loaded (a loaded time range keeps its own total) and "Updated ..." as a live relative time. v3: `renderLogServiceList`, `selectLogService`, `updateLogStatusBar`; logs-viewer.js:87-171, 823-838, 909.
- **LD-10 Terminal toolbar toggles in their meaning colors.** The terminal toolbar's toggles light in their meaning colors when `[aria-pressed="true"]`: Live green (`.ui-log-live`, ok background), Pause amber (`.ui-log-pause`, warn background), other toggles inverted when on (`.ui-log-toggle`, accent background). A font size select (`aria-label="Font size"`; 10, 11, 12 (default), 13, 14, 16px) and a word-wrap toggle (`aria-pressed`; default on with `pre-wrap` + `break-word`, off `pre`) adjust the terminal. v3: `setLogFontSize`, `toggleWordWrap`; ui.css:2349-2351; index.html:1346-1367; logs-viewer.js:1012, 1020.
- **LD-11 A message log timeline merges sources, with source chips.** A message's Logs tab opens with one compact strip instead of the full Overview facts: To (one recipient, taken from the Postfix lines first, which keep the full address with `+tag`), Final Status, Client IP and Relay; no From and no Queue ID (Overview has them). The relay shows its host with a small port chip and the server's IP in a tooltip (MO-4); a host too long for the strip is cut with an ellipsis and its tooltip names it in full. With several recipients the strip drops To and Final Status and keeps Relay only when one server took every tried recipient (TB-27), and the Recipients list follows (OT-18). Then comes one chronological timeline with Postfix and Dovecot lines interleaved, each tagged with its program. Source chips (All, postfix, dovecot; `aria-pressed`, single selection, only when there is more than one source) filter it. With several recipients its head also holds a "Recipient" picker (`md-rcpt-pick`, with a search "Find a recipient", panel "Show the logs of"): "All recipients" first, then each recipient with a status dot and its status word as hint, problems first, then by address; on open it pins the timeline head under the tabs so the list opens downward (DS-14). A pick, or a click on a recipient in the list, shows only that recipient's lines; with no recipient picked, a status or a search in the Recipients list narrows the timeline to the recipients the list shows and the picker names that set (`Deferred "acme" (3)`). A Postfix line belongs to the address the sender wrote (its `orig_to`), a Dovecot line to every address that reached its mailbox; lines of the whole message (connection, queue, bounce notice: no recipient) stay, dimmed (`opacity: .62`) and tagged "All recipients". While narrowed an X button "Show every recipient" clears the pick, the status and the search. The count reads "5 of 12 entries" whenever lines are hidden, else "12 entries"; nothing left reads "No log lines for this filter". A message with only Dovecot lines still gets its timeline. Redraws give the focus back to the control that had it. v3: `renderLogTimeline`, `filterLogTimeline`, `pickMessageRecipient`, `mdLineOwners`, `renderRelay`; message-details.js:277-370, 440-445, 466-524, 768-771, 788-824, 1061-1207; ui.css:429-438, 487-503, 3190-3192.
- **LD-12 Freshness reads the same everywhere: "Updated 3 min ago".** When data was last loaded or checked is a small line under the page title, written as time ago ("Updated 3 min ago", "Checked 2 min ago", "Last fetch done: 2 h ago") with the exact time in a tooltip on hover, and the `uiAgo` labels keep ticking while the page is open: one shared 30000ms timer for all labels, removed elements pruned. Not-yet states read "Not checked yet", "Never fetched"; a failed last run reads in amber with where to look (Devices: "The last check failed. See Status -> Jobs."). DMARC tones the line `ui-text-ok|fail|info` and adds a "View History" link. Pitfall: the line under the title arrived page by page (Domains and Mailbox Statistics in #320, Status in #321) until #386 made Last updated and Last checked say how long ago, kept current while the page is open, and said freshness the same way everywhere. v3: `uiAgo(el, iso, prefix = '')`; utils.js:430-445; app.js:5230-5231; dmarc.js:1136-1184; devices.js:73.
- **LD-13 Progress for long operations.** A long scan shows progress where it runs: "Check all now" on Status, Blocklists starts the check with a POST to `/api/blacklist/check` and opens a panel at the top with "Running Scan...", `"12/50 scanned - <list>"` and a smoothly filling bar (inline width set from polling `/api/blacklist/progress` every 1000ms, `transition: width .3s`); the start toast says "Starting blacklist check..." and the button shows a spinner "Running..." and then returns to the label it had before. The page's refresh keeps the progress panel at the top of the redrawn hosts (TB-10). When done a toast says "Blacklist check completed", the panel goes away and the results reload. A single-host check (the host's "Check now") finishes directly with "Check completed for <host>". A database repair shows "Repairing…", then success or a clear failure; it polls every 2000ms, trusts idle only after 2 polls, and after max 30 polls gives up with "GeoIP repair timed out - check Status page for progress". v3: app.js:5487-5598; settings.js:2569-2644, 2772-2793; ui.css:1704-1706; index.html:1101.
- **LD-14 A click selects a log line, with Copy at its end.** In a log box marked `data-line-select="<line selector>"` a plain click on a line selects the whole line and puts a Copy button at the line's end, outside the selected range: `.ui-line-copy`, `24px` x `22px`, `position: absolute; inset-inline-end: 4px; top: 0`, `aria-label="Copy line"` and `title="Copy line"`. Only a plain click does this: a click on a `button` or `a` in the box, a click whose `detail` is not `1`, Shift+click and a press that moved more than `3px` keep the browser's own selection, so a partial drag, a double click on a word (its second press clears the line selection so the browser selects the word), a triple click and Shift+click work as usual. A press on the button keeps the selection (`preventDefault` on `mousedown`). The button copies the line's text with the Clipboard API, or without HTTPS through a hidden read-only `textarea` and `document.execCommand('copy')`, then selects the line again; it says "Line copied" (the icon becomes a check mark, `.is-copied` in the ok color) or "Could not copy. Press Ctrl+C to copy the selected line.". It goes as soon as the selection no longer equals the line's text, and only one exists at a time. Lines are blocks (`display: block; position: relative; border-radius: 3px; cursor: text`, hover background `rgb(255 255 255 / .06)` only with a pointer; an empty line keeps its height). Used on the Logs page (`.log-line`) and in the container log, which draws one `span.ui-log-line` per line. Live updates ask `uiTextHeld(box)` (a press that started in the box is still down, or the selection touches the box) before they move or replace text: the container log's `2000ms` refresh skips while it is true, checked before the request and again after the answer, and goes on once the selection is cleared. Pitfall: new lines took a selection away, the container log's refresh replaced the lines under it; #474 skips the refresh while text is held, checks again after the answer because selecting can start while the request is out, and ends a press on `mouseup`, a `mousemove` with no button down or window `blur`, so a release outside the window never pauses the refresh for good. v3: `data-line-select`, `uiLineCopy`, `uiLineCopyRemove`, `uiTextHeld`, `uiPressMoved`; utils.js:1488-1503, 1686-1790; ui.css:1166-1176; index.html:1414, 1537; app.js:6344-6392.
- **LD-15 New mail lands at its edge; elsewhere the list offers "N new messages".** The Messages list stays current with every search and filter. Newest first, while the list's first row is in view (in the element that scrolls: the list's own column on wide screens, the page under 1000px; `messagesAtNewEdge`, 8px of slack), the refresh reads the first page with the same query and draws it when it differs from the top of the list shown (`messagesSameAsShown`) as a new list (a new generation that aborts the older list's requests, TB-6), keeping the focus on its row (SV-13) and the docked message, with the outcome counts read again. Oldest first, new mail belongs at the end: while the whole list is loaded and its last row is in view, the refresh reads the list again as long as it is plus the new messages and draws it if anything changed. Anywhere else the list stays as it is: the server counts the messages that came after the list's watermark (`GET /api/messages/new?after_id=<watermark>` with the list's filters answers `{ count, watermark }`; every list answer carries `watermark`, the newest delivery stored when it was read) and the list shows "N new messages" ("1 new message", with thousands separators) at the edge where new mail lands: a sticky pill like the Logs page's New lines (LD-2), `30px` high, `border-radius: 999px`, accent background, 12.5px semibold, an arrow up at the top or down at the end, `10px` below the top or `12px` above the end, and under the search bar where the page scrolls and the bar stays on top (`--ui-msg-new-top`). A click goes to the new mail: newest first, the list loads again from its top and the page scrolls back to the list's start; oldest first, it reads as many rows as are shown plus the new ones (up to 500 a request) and goes to the end. A message is new when a delivery matching the filters was stored after the watermark and none with its Message-ID before it: a status change or another delivery of a message already there is not new. Oldest first while the list is not loaded to its end, nothing is counted or offered: its next pages stop at the watermark (`upto_id`, TB-6), so paging reaches the end and the refresh then takes the new mail in or offers it. Text selected in the list keeps it from being replaced; the count and the offer still update. A time preset runs up to now at every request (MP-8). Nothing happens while the list or a next page loads, and an answer for a list loaded again meanwhile is dropped (SV-7). Keyboard / screen reader: the pill is a `button`. Pitfall: the refresh ran only on the untouched first page (no search, no filter, not scrolled past page 1), so a filtered or scrolled list never showed new mail, and a time preset stayed where it was when picked; #498 follows every filter at the edge, offers the rest like the Logs page and lets the presets run up to now. v3: `smartRefreshMessages`, `messagesAtNewEdge`, `messagesSameAsShown`, `renderMessagesNew`, `messagesShowNew`, `messagesRangeFilters`; app.js:1255-1320, 1322-1415, 1523-1533, 4857-4866, 5031-5092; ui.css:615-622.
