# UI behavior rules (v3 style): Live data and logs

Part of the `v3-ui-style` skill. Companion to `references/v3-design-principles.agents.md` (look, behavior principles, interaction rules, what not to copy). The skill's SKILL.md maps ID prefixes to area files. Paths are relative to the skill folder.

How to read:

- One bullet is one behavior with a stable ID (`DS-1`). A rule may name rules of other areas by ID; when your screen uses that part, read those rules too.
- **Pitfall** marks a behavior whose history shows a failed earlier attempt, a revert or a fixed bug. It says what went wrong and what fixed it. Do not skip it: it is the reason the behavior is shaped the way it is.
- `v3:` gives the v3 helper and `file:line` in the bundled code under `references/v3-code/`, a copy of the mailcow Logs Viewer frontend at commit `0210d15` (`ui.css` is under `assets/css/`). Start at the cited lines and widen to the whole function and what it calls when the bullet is not enough. The rules were first written against the earlier snapshot `deb075d`, then checked rule by rule against this code.
- Rules the interaction fixes changed (October 2026) start with what v3 does now and name its helpers; the part marked "Before the interaction fixes" describes the code before them. Where the two differ, the first part is the rule; details the first part does not cover still hold.
- The principles file's section "Interaction rules v3 follows since its interaction fixes" lists what those fixes added. Never copy anything listed there under "Do not copy".

## Live data and logs

- **LD-1 Live tail with reconnect and a connection state.** The selected service's log streams in live (token from `/api/raw-logs/ws-token`, then `ws(s)://host/ws/raw-logs?service=<id>&token=...`). A dropped connection reconnects by itself after 3000ms while the user stays on the page and is not paused, but not after an authentication failure (close code 4401 or a server error containing "Authentication"); manual disconnects null `onclose` first. When its session ends (sign-out, expiry, a sign-in settings change) the server closes the stream with code 4001; the page reconnects as after any drop, and the token request then sends it to sign-in. A dot and a word show Connected (green), Paused (amber) or Disconnected (red) (`ui-mdot-ok|warn|fail`), so the state is also in text. Pause stops the stream (the button turns into Resume); lines that arrived while paused are not fetched afterwards. While a loaded time range is shown, new live lines are not added and the stream's counts do not replace the range's total, until Live. The Live button clears any range, reloads the newest lines and reconnects. Leaving the Logs page closes the stream. Keyboard: Pause and Live `aria-pressed`. v3: `connectLogWebSocket`, `disconnectLogWebSocket`, `updateWsIndicator`, `toggleLogPause`, `resetToLiveLogs`; logs-viewer.js:751-932, 1093-1116; app.js:1818-1821.
- **LD-2 Follow the end only when the reader is there.** A live log jumps to the newest line only while the reader is already there: check "at end" before appending and scroll only if it was true; scrolling up to read stops the auto-follow, and loading older history never moves the view. Container logs show the last 500 lines and refresh every 2000ms with `silent=true` (no "Loading logs..." flash), test the bottom with `scrollHeight - scrollTop === clientHeight`, and closing stops the polling. A Follow toggle (default on, `aria-pressed`) does the same on the Logs page and scrolls to the newest line (bottom, or top in newest-first order). v3: app.js:5276-5352; logs-viewer.js:534-541, 932.
- **LD-3 Newest first or last, remembered; opens on the newest page.** A toggle flips the display order between classic tail (newest at the bottom) and newest at the top, re-renders what is loaded, and is remembered between visits (`localStorage['logsNewestFirst'] = 'true'|'false'`); its label and icon arrow say where the newest line lives. Keep stored entries chronological and reverse only in rendering (the DOM is reversed per batch). Opening a service shows its newest entries, not the oldest: with page size 500 it reads the total, then fetches the last page. v3: logs-viewer.js:17, 283, 481-483, 545-553.
- **LD-4 Scroll back through history without a jump; a capped live buffer.** Scrolling within 50px of the history edge (the top, or the bottom in newest-first) loads the previous page of 500 older lines, with "Loading older logs..." at that edge; a failure shows "Failed to load older logs", which disappears after 3000ms. The view stays on the same line while they are inserted above: measure the height before and after inserting and add the difference to `scrollTop` (`scrollTop = newHeight - prevHeight` when inserting at the top). A busy server does not slow the tab: the oldest live lines drop off past `MAX_LIVE_LOG_ENTRIES = 5000`, but pages loaded on purpose are not trimmed. v3: logs-viewer.js:328, 400, 452, 514-525.
- **LD-5 Clear stays cleared.** Clear empties the terminal with "Display cleared. New logs will appear here."; the next live lines replace the note. Scrolling up does not bring history back (`oldestPageLoaded = 1`), and a history request already on its way is dropped: increment a view id (`viewId`) on Clear and check it after every await. Search, quick filters and range are cleared too. Pitfall: Clear used to refill the screen with history; #290 made it stay cleared. v3: `viewId`; logs-viewer.js:364, 463, 1202.
- **LD-6 Log lines colored by meaning, matches marked, filters apply to new lines.** Lines are tinted by meaning per service so problems stand out. Generic: red reject, error, blocked, denied, failed, fatal; yellow warning, pregreet, timeout; green sent, connect from, login, delivered, success; gray disconnect, removed, noqueue. API methods GET green, POST yellow, PUT blue, DELETE red, data cut at 200; watchdog by hpdiff and lvl; Rspamd score red at reject threshold (fallback 15), orange at add header (fallback 8), yellow 0 and above, green below 0, subject cut at 80 (`dir="auto"`); time blue, program cyan. The search term is marked in every visible line (`<mark>`, case-insensitive, regex-escaped). With a search or quick filter active, new live lines that do not match arrive hidden (`display: none` plus `.log-filtered`) and the match count updates; while filtering, a pill in the status bar next to the entry count (`.ui-logs-filter`, the app's filter pill; a long search wraps inside it, so it stays in sight while the lines scroll) says "Showing 12 of 500 - filter: "timeout" + Auth failures", with an X (`aria-label` and `title` "Clear all filters") that clears everything. Each service offers its own colored quick-filter chips (`aria-pressed`) with a description tooltip, matching `pattern` on `program` or `message`; chips combine with OR, search with AND; a service with none hides the row. v3: `formatLogLine`, `entryMatchesFilters`, `updateFilterBadge`, `loadSmartFilters`; logs-viewer.js:187, 267, 418-444, 496-532, 591-713, 1172; ui.css:700-701, 2072.
- **LD-7 Quick filters fold to a row and a half.** Many quick-filter chips fold to about one and a half rows with a fade, so the cut second row shows there is more: fold height `round(rowH * 1.6 + 6)`px, `.ui-chip-row.is-folded { max-height: var(--ui-fold-h, 52px); overflow: hidden; mask-image: linear-gradient(to bottom, #000 55%, transparent) }`. "Show all N" next to the Quick Filters title opens them, "Show less" folds again (toggle `aria-expanded`, `aria-controls`). Fold only if `scrollHeight > foldH + rowH`, that is only when it saves at least a full row; an active chip never hides in the folded part (the row opens instead); where chips fit in two rows nothing folds. A ResizeObserver refits only when the rounded width changes. Pitfall: the link first sat under the folded chips (#313); it now follows the Quick Filters title on the same line (#314). Fold only when it saves at least a row, and refit when the chips get their size (the page was hidden, or the width changed). v3: `fitQuickFilters`, `toggleQuickFilters`, `--ui-fold-h`; logs-viewer.js:218-249; ui.css:2274-2283; index.html:1428.
- **LD-8 Range presets load at once; a custom range sits behind a chip.** The range row shows 1h, 6h, 24h, 48h (60, 360, 1440, 2880 minutes) and a Custom chip. A preset fills From and To and loads at once. Custom reveals a From/To row (`datetime-local` `YYYY-MM-DDTHH:MM`) with Load on its own full line (`.ui-logs-custom { flex: 1 1 100% }`) and puts the cursor in From; with no From nothing happens. The fields hold wall times in the app time zone: a preset writes them there and sends its exact instants while the fields still show them; a typed time is read in the app time zone, and To covers its whole minute. Loading a range fetches every page (page size 1000) with "Loading page 3/7...", keeps Load disabled while loading, switches Live off and re-applies active filters. Keyboard: Custom chip `aria-expanded`, `aria-pressed`, `aria-controls="logs-custom-range"`. v3: `setLogTimePreset`, `toggleLogCustomRange`, `loadDateRangeLogs`, `setLogDateInput`, `readLogDateInput`; logs-viewer.js:257, 974-992, 995, 1007; ui.css:2274-2276; index.html:1409-1421.
- **LD-9 Log service list with counts; switching resets the view.** A side list names each log service with an icon (`aria-hidden`) and its number of entries (1000 and more as `1.2K`), kept current by the live stream; the current one is marked (`aria-current="true"`); the default is `postfix`, else the first. Picking another clears the date range, reloads its quick filters, shows its newest lines and reconnects; on narrow screens the picker folds closed into one row that names the current service and its count. A status bar says "1.5K of 12.3K entries" while only part is loaded (a loaded time range keeps its own total) and "Updated ..." as a live relative time. v3: `renderLogServiceList`, `selectLogService`, `updateLogStatusBar`; logs-viewer.js:84-168, 796-811, 882.
- **LD-10 Terminal toolbar toggles in their meaning colors.** The terminal toolbar's toggles light in their meaning colors when `[aria-pressed="true"]`: Live green (`.ui-log-live`, ok background), Pause amber (`.ui-log-pause`, warn background), other toggles inverted when on (`.ui-log-toggle`, accent background). A font size select (`aria-label="Font size"`; 10, 11, 12 (default), 13, 14, 16px) and a word-wrap toggle (`aria-pressed`; default on with `pre-wrap` + `break-word`, off `pre`) adjust the terminal. v3: `setLogFontSize`, `toggleWordWrap`; ui.css:2054-2056; index.html:1368-1389; logs-viewer.js:944, 952.
- **LD-11 A message log timeline merges sources, with source chips.** A message's Logs tab opens with one compact strip (From, To, Final Status, Queue ID, Client IP, Relay) instead of the full Overview facts; long relays truncate with the full value in the tooltip. A per-recipient delivery summary shows only with more than one recipient, with recipients taken from the Postfix lines first (they keep the full address with `+tag`). Then comes one chronological timeline with Postfix and Dovecot lines interleaved, each tagged with its program. Source chips (All, postfix, dovecot; `aria-pressed`, single selection, only when there is more than one source) filter it and the count reads "5 of 12 entries". A message with only Dovecot lines still gets its timeline. v3: `renderLogTimeline`, `filterLogTimeline`; message-details.js:288, 386, 585-603, 693-739.
- **LD-12 Freshness reads the same everywhere: "Updated 3 min ago".** When data was last loaded or checked is a small line under the page title, written as time ago ("Updated 3 min ago", "Checked 2 min ago", "Last fetch done: 2 h ago") with the exact time in a tooltip on hover, and the `uiAgo` labels keep ticking while the page is open: one shared 30000ms timer for all labels, removed elements pruned. Not-yet states read "Not checked yet", "Never fetched"; a failed last run reads in amber with where to look (Devices: "The last check failed. See Status -> Jobs."). DMARC tones the line `ui-text-ok|fail|info` and adds a "View History" link. Pitfall: the line under the title arrived page by page (Domains and Mailbox Statistics in #320, Status in #321) until #386 made Last updated and Last checked say how long ago, kept current while the page is open, and said freshness the same way everywhere. v3: `uiAgo(el, iso, prefix = '')`; utils.js:427-442; app.js:4175-4176; dmarc.js:951-999; devices.js:62.
- **LD-13 Progress for long operations.** A long scan shows progress where it runs: "Check all now" on Status, Blocklists starts the check with a POST to `/api/blacklist/check` and opens a panel at the top with "Running Scan...", `"12/50 scanned - <list>"` and a smoothly filling bar (inline width set from polling `/api/blacklist/progress` every 1000ms, `transition: width .3s`); the start toast says "Starting blacklist check..." and the button shows a spinner "Running..." and then returns to the label it had before. When done a toast says "Blacklist check completed", the panel goes away and the results reload. A single-host check (the host's "Check now") finishes directly with "Check completed for <host>". A database repair shows "Repairing…", then success or a clear failure; it polls every 2000ms, trusts idle only after 2 polls, and after max 30 polls gives up with "GeoIP repair timed out - check Status page for progress". v3: app.js:4432-4543; settings.js:2449-2524, 2652-2673; ui.css:1437-1439; index.html:1118.
