# UI behavior rules (v3 style): Saving, validation and refresh

Part of the `v3-ui-style` skill. Companion to `references/v3-design-principles.agents.md` (look, behavior principles, interaction rules, what not to copy). The skill's SKILL.md maps ID prefixes to area files. Paths are relative to the skill folder.

How to read:

- One bullet is one behavior with a stable ID (`DS-1`). A rule may name rules of other areas by ID; when your screen uses that part, read those rules too.
- **Pitfall** marks a behavior whose history shows a failed earlier attempt, a revert or a fixed bug. It says what went wrong and what fixed it. Do not skip it: it is the reason the behavior is shaped the way it is.
- `v3:` gives the v3 helper and `file:line` in the bundled code under `references/v3-code/`, a copy of the mailcow Logs Viewer frontend at commit `0210d15` (`ui.css` is under `assets/css/`). Start at the cited lines and widen to the whole function and what it calls when the bullet is not enough. The rules were first written against the earlier snapshot `deb075d`, then checked rule by rule against this code.
- Rules the interaction fixes changed (October 2026) start with what v3 does now and name its helpers; the part marked "Before the interaction fixes" describes the code before them. Where the two differ, the first part is the rule; details the first part does not cover still hold.
- The principles file's section "Interaction rules v3 follows since its interaction fixes" lists what those fixes added. Never copy anything listed there under "Do not copy".

## Saving, validation and refresh

- **SV-1 Explicit save with a floating save bar and a dirty count.** Edits are never saved automatically and fields are editable at once, with no Edit mode; dialogs keep their own Save and Cancel. A dark floating bar appears at the bottom center only while something differs from what was loaded ("3 unsaved changes", singular "1 unsaved change", with Discard and Save changes) and disappears at zero: `position: fixed; inset: auto 0 18px 0; z-index: 60; width: fit-content; margin: 0 auto`, ink background, radius 12px, shadow `0 12px 30px rgb(0 0 0 / .25)`. The bar belongs to the page or tab it saves (Settings, the Security Settings tab, a map open on the Rspamd page; switching tab hides it). The last field is never covered: the Security tab reserves room only while its bar shows (`padding-bottom: 90px` via `:has(#security-savebar:not(.hidden))`), the Settings fields column always ends with `padding-bottom: 96px`. While saving both buttons are disabled with `opacity: .6; cursor: wait` and Save reads "Saving...". Phones: `inset: auto 10px calc(76px + env(safe-area-inset-bottom)) 10px; width: auto`, count `flex: 1`. The Settings sidebar marks each section holding a change with a dot (`::after` 7px circle `--ui-info`, `margin-inline-start: auto`). With `form`, Save is a real `type="submit"`; the Settings form is `noValidate`, so the page checks the fields itself (below) instead of the browser's bubbles. Leaving with unsaved changes asks "Leave without saving?" ("You have 3 unsaved changes. Leaving drops them.") with [Stay] then [Leave] on screen, focus on Stay. A page or editor registers how many changes it holds and which moves keep them (Settings keeps them across its sections; Security keeps them across pages, so only the browser leaving asks; a map being edited and a rate limit being edited count too). The sidebar, the search, Refresh, an editor's own way back and Back or Forward ask; Back and Forward are undone while the question is open, so the history stays as it was; closing or reloading the browser tab asks through `beforeunload`. A save makes the saved values the new start, so the reload after it asks nothing about them while another page's changes (Security) are still asked about; signing out asks first and drops the list only once the sign-out worked (a failed sign-out says "Could not sign out. Try again in a moment." and keeps the changes guarded). The question writes no history entry of its own (`data-no-history`), so it never disturbs Back. Before a save every changed field is checked: the first one that fails opens its section, is marked (`aria-invalid` and a note under its line) and takes the focus, a toast names it ("<label>: <problem>", or "N fields need a valid value, starting with <label>"), and nothing is sent; server errors name the field (a FastAPI 422 list as "field: problem"). Screen reader: `role="region" aria-label="Unsaved changes"`; the count is `aria-live="polite"`, so each change is announced. Helpers: `uiSaveBar(id, { save, discard, form })`, `uiSaveBarUpdate(id, count)`, `uiSaveBarBusy(id, true|false)`, `uiUnsavedRegister`, `uiUnsavedCount`, `uiConfirmLeave`, `uiApiErrorText` in utils.js, `settingsCheckFields` in settings.js.Before the interaction fixes (history; where it differs from the text above, the text above is the rule): Edits are never saved automatically and fields are editable at once, with no Edit mode; dialogs keep their own Save and Cancel. - **SV-2 Dirty count against loaded values, without false changes.** The count is the number of distinct fields that differ from a snapshot taken at load (`initialValues` Map by field name); changing a field back drops it from the count, and typing 5 into a field holding 5 is not a change (compare normalised values, numbers arrive as strings). Checkboxes compare as `String(checked)`; listen to `input` and `change`; Clear and Reset fire no event, so recount on the next tick (`setTimeout(updateDirty)`); segmented controls, the Time Zone picker, a choice's Reset and secret buttons dispatch synthetic `input` events; rules compare `JSON.stringify` with quotes stripped. A control that only sets other fields is not counted itself: the Outbound delivery-failure radios (left out by `[name]:not([data-choice])`) and the minutes shown in two options (`data-mirror`) count through the stored fields they set, so a choice changed and changed back leaves nothing to save. A whitelist textarea counts as one change however many lines were edited, ignoring whitespace and blank lines; a map edit is one change with a "Modified" tag, and the count drops back to 0 when the text matches the saved map again (`uiSaveBarUpdate('map-savebar', 0|1)`). An emptied number is saved as 0, switches as true/false. v3: settings.js:1908-1977; protection.js:143-155; smtp-abuse.js:188-197; spam_filter.js:228, 243, 259-268.
- **SV-3 Discard restores; a failed save keeps the edits; one message per save.** Discard drops every edit: Settings re-fetches and redraws (`discard: 'loadSettings()'`), the Security page restores its drafts locally without a round trip. A failed save says "Failed to save: <server detail>"; the bar comes back and the edits stay. Where one bar covers several sources (protection rules, Fail2ban, outgoing spam, whitelist), its count is the sum, Save writes each changed group, and success shows one toast naming what was saved ("Saved the protection rules, Fail2ban and outgoing spam"); a group that fails shows its own error and keeps its changes. v3: `securityChangeCount`, `saveSecuritySettings`, `discardSecuritySettings`; settings.js:1761, 2163-2166; security.js:999-1068.
- **SV-4 Reload after saving only when the app needs it; the toast survives.** Reload the whole app after a save only when it changed a key read once at page load (features, app title and logo, Basic Auth, OAuth2, mailcow URL, time zone; `SETTINGS_READ_AT_PAGE_LOAD`): show "Settings saved - reloading..." or "Features updated - reloading...", then reload after 600ms. For newly disabled purgeable features (the user has confirmed that their stored data is deleted) first show an info toast "Purging data for N disabled feature(s)..."; a purge that fails becomes the message after the reload ("The data of <feature> could not be deleted. Try again."), and Suppressions turned off says what happened to its saved list and this app's Rspamd blocks. Any other save shows "Settings saved" (only if no other toast was shown), redraws Settings in place and stays on the same tab. A message that must be seen after the reload (the credential check result, a purge or Rspamd outcome) travels in `sessionStorage['settingsToastAfterReload']`, read and removed once, private-mode failures ignored. Pitfall: every save sent `disabled_features`, so every save said "Features updated - reloading..." and reloaded, dropping any message shown with it (#394); a toast that must outlive the reload needs sessionStorage (#391). v3: settings.js:2092-2162, 2621-2635.
- **SV-5 Credentials are checked when saved, and the answer says what to fix.** Validate a new or changed Read-Write API key or Rspamd password right after save, and from Validate buttons. Each shows a tag: Not checked, Not configured, Checking…, Accepted, or a specific failure (Rejected, Read-only key, Redirected, Connection error, Unexpected answer); hovering the failure says what to do ("This is a read-only API key. Paste the Read-Write key from System → Configuration → Access → Administrators → API in mailcow."), and the same sentence is the toast. Under it "Checked 14:02" or "Not checked yet"; the answer to a check whose key or password changed while it ran is dropped ("Changed while it was checked. Validate again."). If one check fails, its failure wins over another's success; both places in Settings that show a check update together, and the About cards show the last result ("Accepted", the failure, or "It has not been checked yet."). Without the credential, Validate stays visible but disabled with a reason ("Add a Read-Write API key first" / "Add the Rspamd password first" / "Add a MaxMind Account ID and License Key first"). The MaxMind licence check turns every badge into "Checking…" and keeps the result across redraws until the next full load. Besides the page, the Credential Checks job checks each saved key and password (also one set by ENV) 30 seconds after a start and every 6 hours, keeps a result only while its key is still the one saved, and a failure marks the job failed on Status ("... See Settings > Mailcow."). Pitfall: a rejected or read-only key was only found out when an action failed (#391). The page never retries a check on its own: a rejected key or password is a failed login for mailcow's Fail2ban, so every check with a wrong one, a manual Validate or a run of the job, counts as one. v3: settings.js:1529-1537, 2061-2084, 2401-2447, 2526-2650; about.js:74-117.
- **SV-6 Never redraw what the user is working on.** Before any background redraw (the 30-second refresh included), each page asks whether the user is working there: skip Settings while `#settings-edit-form` is in visible `#settings-content`, and let the late version check redraw it only while it holds no unsaved changes; skip Security cards while a card is open, a change is unsaved or focus is in a card (`securityEditing()`); skip the Lists only while an Add field has text (`securityListsTyping()`); keep rule and whitelist drafts on screen; refresh nothing while `#message-modal` is visible and not `.ui-docked`; Outbound refreshes the suppression list only while its Suppressions tab is open and skips while `#add-suppression-modal` or `#edit-suppression-modal` is open or the list is still loading; the Rspamd page, with its map editor, is never refreshed on the timer. Pitfall: background refreshes wiped unsaved rule edits and Fail2ban typing until #325 and #327 guarded them (Security cards and Lists in #349); #368 narrowed the Lists guard to only while an address is typed into an Add field because it had blocked legitimate redraws. A narrower guard is better than one that blocks real updates. v3: app.js:1122-1126, 1700-1705, 2471-2472; security.js:99-101, 506-518; protection.js:39-43; smtp-abuse.js:12, 125; spam_filter.js:23; app.js:1143-1150, 1846-1848; settings.js:1458.
- **SV-7 Stale answers are dropped; one request for many callers.** When a filter, page or view changes quickly, drop an older slower answer instead of letting it replace what was asked for last: increment a request counter per request and apply the answer only if it is still the latest; check view guards (current view, current domain) after every await; bump a view id on Clear; compare identity (`rateLimitSelectedSender !== user`). Several callers asking for a refresh at once cause a single request (debounce 150ms). Example: search cancels with `AbortController` instead (SR-5). v3: `refreshSecurityAddresses`; security.js:23, 155-202; dmarc.js:547, 1147, 1240; devices.js:36, 51; mailbox-stats.js:259, 291; logs-viewer.js:333, 364, 1213; rate-limits.js:541.
- **SV-8 Paint what you have now, fill in the rest quietly.** Render at once from what is already held, then fetch and repaint only the changed block. Settings renders with the cached version, then refreshes version and update status in the background ("Checking..." until known, "Not known" with a "Check failed" tag when the latest version could not be read) and repaints with them only while Settings holds no unsaved changes. Going back to the DMARC domain list paints the previous list instantly and refreshes it behind; only the first visit shows a spinner. A blocked sender's detail shows at once with the refused messages the list carried, then the complete history replaces only the messages block so the header never flickers; a muted line "Loading full history..." replaces a spinner. One request per sender, cached until the page data reloads, with an in-flight guard; a failed read is retried next time; failure line "Showing the latest 5 only - full history failed to load"; "Showing 200 of 1,240" when capped. v3: settings.js:1423-1522; dmarc.js:165-200; rate-limits.js:394-397, 466-546.
- **SV-9 Cache what is stable, re-read what may change elsewhere.** Decide per data source: data that does not change while the user moves around is read once and reused, data another page can change is re-read on each visit, and a full reload throws away derived caches so nothing stale shows with new data. DMARC domain read once per domain (5 parallel requests, cache key the domain name), fresh when opened from the address; domain search list fetched once and reused for 60000ms; Settings version info not refetched by the 30s refresh; DMARC controls re-read `/api/dmarc/imap/status` and `/api/settings/info` on every view; rate-limit reload drops per-sender histories and closes open forms. v3: search.js:140-155; app.js:1090-1094, 1710-1716; dmarc.js:157, 182, 435, 543; rate-limits.js:71-76.
- **SV-10 Auto-refresh the open page only, quietly.** The page in view refreshes itself every 30 seconds (`AUTO_REFRESH_INTERVAL = 30000`) without a spinner, and does not redraw when nothing changed (JSON string compare against `lastDataCache[key]`), so it never flickers or loses place; combine with SV-6. A page that says it is disabled asks for nothing. Each page refreshes its own set (dashboard figures, activity, chart, status and security cards; Security events, overview, Fail2ban data and hits; Outbound the queue, plus the suppression list on its Suppressions tab or only the suppression counts on the Queue tab; Quarantine; Status fully; Settings); the Rspamd page is not on the timer, so its map editor never loses typing. Messages refreshes only on the untouched first page (no search, no filter, not scrolled past page 1). There is one Refresh in the shell (sidebar or phone top bar), not one per page (#318: Status has no Refresh button of its own); it reloads the current page and the counters, and on DMARC first clears the server cache while keeping the open view. v3: `startAutoRefresh`, `smartRefreshCurrentTab`, `hasDataChanged`; app.js:460-462, 1096-1188, 1656-1681, 1856-1858, 1881-1893, 1119-1121, 1846-1848.
- **SV-11 Show the result at once, confirm it later.** Update the screen at once after an action, then read again once when the server applies it with a delay. After Unban the address leaves the lists immediately, the toast names what was lifted (the network, when Fail2ban had banned the whole network around the address), and Fail2ban is asked again 5000ms later (and on the 30s refresh); a ban mailcow is about to lift is not shown as banned; a single address's own prefix (`/32` for IPv4, `/128` for IPv6) is ignored when matching, while an IPv6 `/32` stays a whole network. After a ban or undo, everything that shows it reloads so Overview and Lists agree. "Fetch reports" re-reads the status at once (to show Running) and again 5 seconds later; `already_running` gives info "Reports are already being fetched". "Run now" reloads Status after 1000ms; HTTP 409 gives warning "Job "<name>" is already running". A suppression change is synced with Rspamd in the background (the server skips it while Sync with Rspamd is off): what changed in Rspamd comes into the list first ("List updated from Rspamd: N added, M deleted."), then the list, its counts and the sync note reload; there is no manual sync button. A one-domain DNS check redraws just that row, still open; Check all reloads after 1000ms and "DNS check already in progress" is refused. Keyboard: buttons are disabled while working. Pitfall: mailcow queues an unban and lifts it a few seconds later, but the page reloaded the bans at once and never again until a page reload, so the address stayed under Banned (#356); the delayed re-read fixed it. v3: app.js:1462-1472, 4917-4960; protection.js:241-246; dmarc.js:1001; domains.js:364-443; spam_filter.js:1118, 1133; app.js:1436-1446; spam_filter.js:1110-1113.
- **SV-12 Validation names the bad entry and keeps the text.** Validate per entry, name the refused entry and keep the field's text: an unknown country says "No such country. Pick one from the list, or type its two-letter code."; an address list names the bad entry (address fields accept commas, semicolons or spaces); a map that fails validation lists "Line 12: <error> - <content>" with warnings in amber after errors, and Save refuses with "Cannot save: 3 validation error(s). Fix them first."; map status tags "Valid", "Valid, 2 warning(s)", "3 error(s)", "Validation failed", "Saved". When the server rewrites entries the editor shows the saved form and the toast says how many were changed. Pitfall: two addresses separated by a comma were refused (501 Bad recipient address syntax) and no notification arrived, while Settings saved the value without a word; #420 fixed it, and Test SMTP now lists who it sent to and what it skipped. v3: protection.js:194-200; spam_filter.js:270, 311.
