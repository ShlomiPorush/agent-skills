# UI behavior rules (v3 style): Saving, validation and refresh

Part of the `v3-ui-style` skill. Companion to `references/v3-design-principles.agents.md` (look, behavior principles, interaction rules, what not to copy). The skill's SKILL.md maps ID prefixes to area files. Paths are relative to the skill folder.

How to read:

- One bullet is one behavior with a stable ID (`DS-1`). A rule may name rules of other areas by ID; when your screen uses that part, read those rules too.
- **Pitfall** marks a behavior whose history shows a failed earlier attempt, a revert or a fixed bug. It says what went wrong and what fixed it. Do not skip it: it is the reason the behavior is shaped the way it is.
- `v3:` gives the v3 helper and `file:line` in the bundled code under `references/v3-code/`, a copy of the mailcow Logs Viewer frontend at commit `8caf6e4` (`ui.css` is under `assets/css/`). Start at the cited lines and widen to the whole function and what it calls when the bullet is not enough. The rules were first written against the earlier snapshot `deb075d`, then checked rule by rule against this code.
- Rules the interaction fixes changed (October 2026) start with what v3 does now and name its helpers; the part marked "Before the interaction fixes" describes the code before them. Where the two differ, the first part is the rule; details the first part does not cover still hold. A sentence that starts "Before the auto-refresh layer" describes older code in the same way: history, not the rule.
- The principles file's section "Interaction rules v3 follows since its interaction fixes" lists what those fixes added. Never copy anything listed there under "Do not copy".

## Saving, validation and refresh

- **SV-1 Explicit save with a floating save bar and a dirty count.** Edits are never saved automatically and fields are editable at once, with no Edit mode; dialogs keep their own Save and Cancel. A dark floating bar appears at the bottom center only while something differs from what was loaded ("3 unsaved changes", singular "1 unsaved change", with Discard and Save changes) and disappears at zero: `position: fixed; inset: auto 0 18px 0; z-index: 60; width: fit-content; margin: 0 auto`, ink background, radius 12px, shadow `0 12px 30px rgb(0 0 0 / .25)`. The bar belongs to the page or tab it saves (Settings, the Security Settings tab, a map open on the Rspamd page; switching tab hides it). The last field is never covered: the Security tab reserves room only while its bar shows (`padding-bottom: 90px` via `:has(#security-savebar:not(.hidden))`), the Settings fields column always ends with `padding-bottom: 96px`. While saving both buttons are disabled with `opacity: .6; cursor: wait` and Save reads "Saving...". Phones: `inset: auto 10px calc(76px + env(safe-area-inset-bottom)) 10px; width: auto`, count `flex: 1`. The Settings sidebar marks each section holding a change with a dot (`::after` 7px circle `--ui-info`, `margin-inline-start: auto`). With `form`, Save is a real `type="submit"`; the Settings form is `noValidate`, so the page checks the fields itself (below) instead of the browser's bubbles. Leaving with unsaved changes asks "Leave without saving?" ("You have 3 unsaved changes. Leaving drops them.") with [Stay] then [Leave] on screen, focus on Stay. A page or editor registers how many changes it holds and which moves keep them (Settings keeps them across its sections; Security keeps them across pages, so only the browser leaving asks; a map being edited and a rate limit being edited count too). The sidebar, the search, an editor's own way back and Back or Forward ask; Back and Forward are undone while the question is open, so the history stays as it was; closing or reloading the browser tab asks through `beforeunload`. A save makes the saved values the new start, so the reload after it asks nothing about them while another page's changes (Security) are still asked about; signing out asks first and drops the list only once the sign-out worked (a failed sign-out says "Could not sign out. Try again in a moment." and keeps the changes guarded). The question writes no history entry of its own (`data-no-history`), so it never disturbs Back. Before a save every changed field is checked: the first one that fails opens its section, is marked (`aria-invalid` and a note under its line) and takes the focus, a toast names it ("<label>: <problem>", or "N fields need a valid value, starting with <label>"), and nothing is sent; server errors name the field (a FastAPI 422 list as "field: problem"). Screen reader: `role="region" aria-label="Unsaved changes"`; the count is `aria-live="polite"`, so each change is announced. - **SV-2 Dirty count against loaded values, without false changes.** The count is the number of distinct fields that differ from a snapshot taken at load (`initialValues` Map by field name); changing a field back drops it from the count, and typing 5 into a field holding 5 is not a change (compare normalised values, numbers arrive as strings). Checkboxes compare as `String(checked)`; listen to `input` and `change`; Clear and Reset fire no event, so recount on the next tick (`setTimeout(updateDirty)`); segmented controls, the Time Zone picker, a choice's Reset and secret buttons dispatch synthetic `input` events; rules compare `JSON.stringify` with quotes stripped. A control that only sets other fields is not counted itself: the Outbound delivery-failure radios (left out by `[name]:not([data-choice])`) and the minutes shown in two options (`data-mirror`) count through the stored fields they set, so a choice changed and changed back leaves nothing to save. A whitelist textarea counts as one change however many lines were edited, ignoring whitespace and blank lines; a map edit is one change with a "Modified" tag, and the count drops back to 0 when the text matches the saved map again (`uiSaveBarUpdate('map-savebar', 0|1)`). An emptied number is saved as 0, switches as true/false. v3: settings.js:1955-2026; protection.js:145-157; smtp-abuse.js:218-227; spam_filter.js:253, 268, 284-293.
- **SV-3 Discard restores; a failed save keeps the edits; one message per save.** Discard drops every edit: Settings re-fetches and redraws (`discard: 'loadSettings()'`), the Security page restores its drafts locally without a round trip. A failed save says "Failed to save: <server detail>"; the bar comes back and the edits stay. Where one bar covers several sources (protection rules, Fail2ban, outgoing spam, whitelist), its count is the sum, Save writes each changed group, and success shows one toast naming what was saved ("Saved the protection rules, Fail2ban and outgoing spam"); a group that fails shows its own error and keeps its changes. v3: `securityChangeCount`, `saveSecuritySettings`, `discardSecuritySettings`; settings.js:1808, 2212-2215; security.js:1038-1107.
- **SV-4 Reload after saving only when the app needs it; the toast survives.** Reload the whole app after a save only when it changed a key read once at page load (features, app title and logo, Basic Auth, OAuth2, mailcow URL, time zone; `SETTINGS_READ_AT_PAGE_LOAD`): show "Settings saved - reloading..." or "Features updated - reloading...", then reload after 600ms. For newly disabled purgeable features (the user has confirmed that their stored data is deleted) first show an info toast "Purging data for N disabled feature(s)..."; a purge that fails becomes the message after the reload ("The data of <feature> could not be deleted. Try again."), and Suppressions turned off says what happened to its saved list and this app's Rspamd blocks. Any other save shows "Settings saved" (only if no other toast was shown), redraws Settings in place and stays on the same tab. A message that must be seen after the reload (the credential check result, a purge or Rspamd outcome) travels in `sessionStorage['settingsToastAfterReload']`, read and removed once, private-mode failures ignored. Pitfall: every save sent `disabled_features`, so every save said "Features updated - reloading..." and reloaded, dropping any message shown with it (#394); a toast that must outlive the reload needs sessionStorage (#391). v3: settings.js:2141-2211, 2670-2684.
- **SV-5 Credentials are checked when saved, and the answer says what to fix.** Validate a new or changed Read-Write API key or Rspamd password right after save, and from Validate buttons. Each shows a tag: Not checked, Not configured, Checking…, Accepted, or a specific failure (Rejected, Read-only key, Redirected, Connection error, Unexpected answer); hovering the failure says what to do ("This is a read-only API key. Paste the Read-Write key from System → Configuration → Access → Administrators → API in mailcow."), and the same sentence is the toast. Under it "Checked 14:02" or "Not checked yet"; the answer to a check whose key or password changed while it ran is dropped ("Changed while it was checked. Validate again."). If one check fails, its failure wins over another's success; both places in Settings that show a check update together, and the About cards show the last result ("Accepted", the failure, or "It has not been checked yet."). Without the credential, Validate stays visible but disabled with a reason ("Add a Read-Write API key first" / "Add the Rspamd password first" / "Add a MaxMind Account ID and License Key first"). The MaxMind licence check turns every badge into "Checking…" and keeps the result across redraws until the next full load. Besides the page, the Credential Checks job checks each saved key and password (also one set by ENV) 30 seconds after a start and every 6 hours, keeps a result only while its key is still the one saved, and a failure marks the job failed on Status ("... See Settings > Mailcow."). Pitfall: a rejected or read-only key was only found out when an action failed (#391). The page never retries a check on its own: a rejected key or password is a failed login for mailcow's Fail2ban, so every check with a wrong one, a manual Validate or a run of the job, counts as one. v3: settings.js:1574-1582, 2110-2133, 2450-2496, 2575-2699; about.js:74-117.
- **SV-6 Never redraw what the user is working on.** A background refresh asks whether the user is working in the part it would redraw, and asks again when its answer arrives, since the user may have started meanwhile; it asks about that part only, never about unsaved changes elsewhere (Security keeps drafts across pages). Working means: a window of the page open over it, unsaved changes in it, text selected in it (`uiTextHeld`), the keyboard on one of its controls, or one of its actions running. What each page checks in v3: skip Settings while `#settings-edit-form` is in visible `#settings-content`, and let the late version check redraw it only while it holds no unsaved changes; skip Security cards while a card is open, a change is unsaved or focus is in a card (`securityEditing()`); skip the Lists only while an Add field has text (`securityListsTyping()`); keep rule and whitelist drafts on screen; the Outgoing spam panel is not read while the focus is in it or text in it is selected, nor drawn if that started meanwhile, and an unsaved whitelist stays as typed; refresh nothing while `#message-modal` is visible and not `.ui-docked` (DS-13); Outbound refreshes the suppression list only while its Suppressions tab is open and skips while `#add-suppression-modal` or `#edit-suppression-modal` is open or the list is still loading; the Queue and the Quarantine are neither read nor drawn while one of their actions runs; the Rspamd maps list is read only while the list is shown (never while a map is open in the editor or loading into it) and drawn only while no text in it is selected; Domains is neither read nor drawn while a DNS check runs, and not drawn while text in its list is selected; DMARC & TLS reads nothing while its record, Manage Reports or sync history window is open, text in the view is selected or the focus is on a control in the view other than a calendar day, which the redraw gives back (`dmarcBusy`); Mailbox Statistics is neither read nor drawn while text in its list is selected or a load of it is on its way; Rate Limits reads nothing while a limit is open for editing, the bulk panel is open, a field of the view has the focus or text is selected, and checks again on the answer; Devices is not drawn while its type picker has the focus or text in its list is selected (checked on the answer only); Status draws a section only while no text in it is selected and the keyboard is not on one of its controls (`statusHold`, `:focus-visible`), else that section waits for the next refresh; Messages takes new mail into the list only while no text in it is selected (LD-15); the container log skips while text is held (LD-14). A redraw that passes keeps the user's place (SV-13). Pitfall: background refreshes wiped unsaved rule edits and Fail2ban typing until #325 and #327 guarded them (Security cards and Lists in #349); #368 narrowed the Lists guard to only while an address is typed into an Add field because it had blocked legitimate redraws. A narrower guard is better than one that blocks real updates. Before the auto-refresh layer the Rspamd page was not on the timer at all (#503 changed that), so its map editor could not lose typing but its list never refreshed; the layer refreshes the list and leaves the editor out. v3: `securityEditing`, `securityListsTyping`, `dmarcBusy`, `statusHold`, `uiTextHeld`; app.js:1165-1181, 1936-1977, 2002-2042, 5251-5255; security.js:99-101, 547-557; protection.js:39-43; smtp-abuse.js:43-65; spam_filter.js:23-34, 89-110; domains.js:75-95; dmarc.js:129-155; mailbox-stats.js:192-245; rate-limits.js:127-166; devices.js:39-71; settings.js:1503; utils.js:1752-1757.
- **SV-7 Stale answers are dropped; one request for many callers.** When a filter, page or view changes quickly, drop an older slower answer instead of letting it replace what was asked for last: increment a request counter per request and apply the answer only if it is still the latest; check view guards (current view, current domain) after every await; bump a view id on Clear; compare identity (`rateLimitSelectedSender !== user`); DMARC numbers every load of a view, the user's or the refresh's, and only the newest draws (`dmarcLoadSeq`), so an answer for a sender or a day the user has left is dropped; the Quarantine's full load, its refresh and the reload after an action share one order (`quarantineAsked`, `quarantineTakeTurn`), so an older answer never brings back a message already handled; Rate Limits drops a refresh asked before a load, an edit, a save or a bulk apply (`rateLimitsGen`). - **SV-8 Paint what you have now, fill in the rest quietly.** Render at once from what is already held, then fetch and repaint only the changed block. Settings renders with the cached version, then refreshes version and update status in the background ("Checking..." until known, "Not known" with a "Check failed" tag when the latest version could not be read) and repaints with them only while Settings holds no unsaved changes. - **SV-9 Cache what is stable, re-read what may change elsewhere.** Decide per data source: data that does not change while the user moves around is read once and reused, data another page can change is re-read on each visit, and a full reload throws away derived caches so nothing stale shows with new data. - **SV-10 Every page updates by itself, quietly; there is no Refresh button.** Nothing asks the user to refresh: there is no Refresh in the shell (sidebar foot, phone top bar), on a page or in a panel. The open page reads its data again by itself, without a spinner, and draws only what changed (a JSON string compare against what it shows: `hasDataChanged` with `lastDataCache[key]`, or the page's own last answer; the Dashboard's Needs attention compares the markup it would draw), so it never flickers or loses place; combine with SV-6 (when not to draw) and SV-13 (what a draw keeps). One scheduler: each page registers how often it refreshes and what it reads (`registerPageRefresh(route, every, run)`, `every` a number or a function of the open view), and a tick every 30 seconds (`PAGE_REFRESH_TICK = 30000`) runs the open page's refresher when its time is due (2 seconds of slack) and its last run is done; a page just opened counts from its load (`pageRefreshLoaded`). The pace follows how often the data can change: every 30 seconds the Dashboard (the mail flow, the status and Security cards), Messages, Security (events, overview, Fail2ban data and rule hits), Outbound (the queue, plus the suppression list on its Suppressions tab or only its counts on the Queue tab), Quarantine (with the Auto-Rules tab's rules, hits and open history), Status and Settings; every minute Devices (as often as the ActiveSync log is read), the Rspamd maps list, Rate Limits and the Outgoing spam panel on Security (checked inside the Security run, `smtpAbuseLoadedAt`); every 5 minutes Domains (mailcow is asked for the domains on each read), DMARC & TLS (the server keeps its lists 5 minutes), Mailbox Statistics (`mailboxStatsRefreshEvery()`: 60 seconds on its Rate Limits view, 5 minutes on Statistics, as often as mailcow's statistics are fetched) and, inside the Dashboard's run, its blocklist and health figures (`dashboardKpisAt`) and trends. Mail flow asks for its period again every minute (`60000`ms) for 24 hours and every 5 minutes (`300000`ms) for 7 and 30 days, and while zoomed refreshes only the strip and its limits and keeps the zoom (CH-10); after a failed load it asks again on the next tick, and under a gesture it asks nothing; an answer made stale by a period or zoom change is dropped (SV-7). The sidebar counters are read every 5 minutes, checked by their own 30-second timer with the same hidden-tab rule (NL-10), Needs attention on its own timers on every page (NL-19). A hidden browser tab starts nothing: the tick, the counters, Needs attention and the container log's poll wait, and once the tab is shown the open page catches up (`visibilitychange`); a read already on its way is not cancelled, and live work the user started goes on (the Logs stream, a running blocklist scan's progress). A page that says it is disabled asks for nothing, and nothing refreshes while a message is open as a dialog over the page (DS-13). A run that has not finished in 20 seconds (`PAGE_REFRESH_TIMEOUT = 20000`) frees the next one (`Promise.race`; the run itself is not cancelled), so a read that hangs never holds the next refresh; reads that pass `authenticatedFetch(url, { timeout })` are aborted at 20 seconds, the body included (Messages, Quarantine, Domains, Devices, DMARC, Mailbox Statistics, Rate Limits, the Rspamd maps, Outgoing spam, the Auto-Rules tab), while the others (the Queue, Settings, parts of the Dashboard) may still be on their way. A background read that fails keeps what is shown, except in v3: the Dashboard's blocklist figure and the figures at the top of Status turn into "-", a failed Security overview read replaces the address list with "Failed to load: <reason>", and a failed suppression list read replaces that list the same way; do not copy that. Some parts also draw without comparing: the Status sections, the Outbound suppression list, and the Dashboard's Security card and system summary (read again and drawn on every refresh, with no check for selected text and without keeping the focus); do not copy that either. A page whose first load failed shows the failure with Try again where it has one, and its own refresh tries again (FB-3): DMARC on the next tick (`pageRefreshRetry`), the other pages at their own pace. Messages takes new mail in where it lands, with every search and filter, and offers "N new messages" anywhere else (LD-15); a time preset runs up to now at every request (MP-8). The UI does not clear the server's DMARC cache, so DMARC can be up to about 10 minutes old (an import or a delete clears it on the server). Pitfall: the Messages refresh drew its answer over a list that had been loaded again meanwhile, so an answer for old filters or an old order could replace the list shown, and after a failed load the old cached answer stayed, so the next refresh saw no change and drew nothing; #477 makes it wait while the list loads, check again after its answer and draw a change as a new list, and a failed load clears the cached answer so the next refresh draws what it gets. Before the auto-refresh layer one 30-second timer refreshed only the Dashboard, Messages, Security, Outbound, Quarantine, Status and Settings: Domains, DMARC, Mailbox Statistics, Rate Limits, Devices and the Rspamd list stayed as first loaded until the shell's Refresh (which reloaded the page and the counters, and on DMARC cleared the server cache), and Messages stopped refreshing as soon as a search or filter was set or a second page loaded; the layer (#497 to #504) gave every page its own pace (#497, #499 to #503), let Messages follow every filter (#498, LD-15) and removed every Refresh button (#504). v3: `registerPageRefresh`, `pageRefreshTick`, `pageRefreshNow`, `pageRefreshLoaded`, `pageRefreshRetry`, `startPageRefresh`, `hasDataChanged`, `smartRefreshDashboard`, `refreshMailFlowChart`, `mailboxStatsRefreshEvery`, `authenticatedFetch`; app.js:95-132, 1131-1196, 1198-1242, 1245-1253, 1983-1999, 2093-2095, 2911-2916, 5663-5693; mailbox-stats.js:180-186; dmarc.js:80-85, 141-155; smtp-abuse.js:16-17, 43-65.

- **SV-13 When a refresh does redraw, the user's place is kept.** A redraw that SV-6 lets through gives back what the user had. The keyboard focus goes back to the same control in the same row: the row found again by its key attribute, the control by its tag and its `aria-label` or text, else by its place among the row's controls (a count on it may have changed), else the row (`uiKeepFocus(container, keyAttr, draw)`: Messages by `data-key`, Domains by `data-domain-row`, Mailbox Statistics by `data-ms-user`; Needs attention and the Auto-Rules tab replace their markup with `uiReplaceKeepingFocus`, charts redraw with `uiRedrawKeepingFocus`). The row the user was looking at stays where it was on the screen: the first row in view is found again by its key and the scroller moves by as much as it moved, so rows added or removed above it do not move the view (`uiKeepRowInView(list, rowSelector, keyAttr, draw)`, scrolling the nearest element that scrolls, else the page, `uiScrollParent`; Domains, Mailbox Statistics). Checked rows stay checked (TB-12), open rows and groups stay open (TB-10), a redrawn sheet keeps its scroll and grown height (DS-7), an open picker stays open (MP-2), the message open in the reading pane stays marked (TB-20), and DMARC keeps the page's scroll, the calendar's scroll and its focused day. Focus comes back with `preventScroll: true`, so giving it back never scrolls. Keyboard: a keyboard user working down a list never loses their place to a refresh. v3: `uiKeepFocus`, `uiKeepRowInView`, `uiScrollParent`, `uiReplaceKeepingFocus`, `uiRedrawKeepingFocus`, `dmarcShow`; utils.js:1726-1748, 2215-2248, 2969-2991; app.js:1283, 2432-2455, 5107; domains.js:213-218; mailbox-stats.js:232-234; dmarc.js:102-124.
